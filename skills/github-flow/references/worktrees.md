# Worktree location and lifecycle

For each Git repository under `C:\Offline\Repozytoria`, the target location is `<primary-checkout>/worktrees/<task-or-issue>`. It is a local ignored directory, not another tracked copy of the project. Identify the primary checkout with Git's worktree registry; when already in a linked worktree, do not nest a new root under it. A future monorepo shares a root per actual Git repository; a project without a Git repository is not ready for Git worktrees. Detect paths, reparse points, worktree registrations and existing files before making changes.

Before first use, ensure `worktrees/` is ignored and contains no tracked entries: use `git ls-files -- worktrees/` and verify the effective rule with `git check-ignore -v --no-index worktrees/<probe>`. Prefer an existing project rule. For a local-only setup, an anchored `/worktrees/` rule in the main Git directory's `info/exclude` avoids changing tracked project files; preserve existing rules, use the Git-resolved path, and verify afterwards. Local exclude does not travel to other clones. Do not create or modify a separate Project manifest just for this preference.

When an issue reaches verified `done`, promptly inspect its associated worktree, not every worktree in the repository. A PR merge, passing CI, age, or an old snapshot alone is not `done`. Re-read the live issue/Project state, PR and branch relationship; a failed read is unknown. Confirm the registry and exact canonical path, repository ownership, no lock, no running consumer, clean tracked and untracked state, no unpreserved work or unique commits, and integration/preservation of the branch. Check ignored files and junctions too: normal `git status` can miss user data. Treat secrets, user-created files, unknown ignored data, unverified status, dirty or locked worktrees, active PRs and active consumers as needs-review; do not delete them merely because the issue says done.

If the worktree is clean, fully integrated, inactive and any ignored data is proven disposable or preserved, use the project's existing authorized worktree lifecycle owner; otherwise use `git worktree remove <exact-path>` without `--force` under the appropriate authority. Re-read state immediately before removal and verify the worktree registry and directory after it. Never recursively delete the directory directly, prune unrelated registrations, remove branch/history, detach a junction's target, or broaden an uncertain selection. If validation or removal fails, stop and report the specific reason. Schedule or hook-based cleanup is not implied by this instruction.

VSone uses its own `agent:worktree` lifecycle owner. In versions containing the per-repository worktree change, use its current instructions for the ignored primary-checkout root and issue-targeted cleanup after confirmed `done`. Older checkouts can still contain the previous helper: follow the instructions and capabilities of the checked-out version rather than assuming it has been updated. Keep the former external root in the inventory, do not silently migrate or delete its worktrees, and do not create a second cleanup controller.

The current VSone cleanup checks that the worktree branch is an ancestor of `smoke`. A squash or rebase merge may leave the branch outside that ancestry and therefore require manual review even when its changes are integrated. Preserve the branch and do not bypass the guard; when the repository permits it, retain branch ancestry during merge if later automatic cleanup is intended.
