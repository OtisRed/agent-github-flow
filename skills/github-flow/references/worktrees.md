# Worktree location and lifecycle

For each Git repository under `C:\Offline\Repozytoria`, the target location is `<primary-checkout>/worktrees/<task-or-issue>`. It is a local ignored directory, not another tracked copy of the project. If the active host requires a managed worktree lifecycle and chooses a different location, use that host's creation and archive tools and preserve its chosen location; do not duplicate or move a live worktree just to match the target path. This host constraint does not change the target for other workflows. If the host refuses to archive the active primary worktree, first select another existing workspace through the host; do not bypass that guard with Git deletion. Identify the primary checkout with Git's worktree registry; when already in a linked worktree, do not nest a new root under it. A future monorepo shares a root per actual Git repository; a project without a Git repository is not ready for Git worktrees. Detect paths, reparse points, worktree registrations and existing files before making changes.

Before creating the worktree, verify the origin repository and fetch main and smoke. Compare full refs/heads/main and refs/remotes/origin/main. If behind, fast-forward the clean main checkout with git pull --ff-only origin main and recheck equality. If unavailable, dirty and needing an update, ahead or diverged, report the discrepancy before creating the worktree. Always branch from the fetched origin/smoke.

Before first use, ensure `worktrees/` is ignored and contains no tracked entries: use `git ls-files -- worktrees/` and verify the effective rule with `git check-ignore -v --no-index worktrees/<probe>`. Prefer an existing project rule. For a local-only setup, an anchored `/worktrees/` rule in the main Git directory's `info/exclude` avoids changing tracked project files; preserve existing rules, use the Git-resolved path, and verify afterwards. Local exclude does not travel to other clones. Do not create or modify a separate Project manifest just for this preference.

When an issue reaches verified `done`, promptly inspect its associated worktree, not every worktree in the repository. A PR merge, passing CI, age, or an old snapshot alone is not `done`. Re-read the live issue/Project state, PR and branch relationship; a failed read is unknown. Confirm the registry and exact canonical path, repository ownership, no lock, no running consumer, clean tracked and untracked state, no unpreserved work or unique commits, and integration/preservation of the branch. Check ignored files and junctions too: normal `git status` can miss user data. Treat secrets, user-created files, unknown ignored data, unverified status, dirty or locked worktrees, active PRs and active consumers as needs-review; do not delete them merely because the issue says done.

If the worktree is clean, fully integrated, inactive and any ignored data is proven disposable or preserved, use the project's existing authorized worktree lifecycle owner; otherwise use `git worktree remove <exact-path>` without `--force` under the appropriate authority. Re-read state immediately before removal and verify the worktree registry and directory after it. Never recursively delete the directory directly, prune unrelated registrations, detach a junction's target, or broaden an uncertain selection. If validation or removal fails, stop and report the specific reason. Schedule or hook-based cleanup is not implied by this instruction.

VSone uses its own `agent:worktree` lifecycle owner. In versions containing the per-repository worktree change, use its current instructions for the ignored primary-checkout root and issue-targeted cleanup after confirmed `done`. Older checkouts can still contain the previous helper: follow the instructions and capabilities of the checked-out version rather than assuming it has been updated. Keep the former external root in the inventory, do not silently migrate or delete its worktrees, and do not create a second cleanup controller.

The current VSone cleanup checks that the worktree branch is an ancestor of `smoke`. A squash or rebase merge may leave the branch outside that ancestry and therefore require manual review even when its changes are integrated. Preserve the branch and do not bypass the guard; when the repository permits it, retain branch ancestry during merge if later automatic cleanup is intended.

## At closure after merge to smoke

1. Verify the PR was merged into this repository's smoke. Record its head repository, task branch and full merged PR head SHA. Fetch origin/smoke. In the clean checkout actually on smoke, run `git pull --ff-only origin smoke`. If smoke is not checked out, create the local tracking branch when missing, or fast-forward the unoccupied local ref with an expected-old-SHA update after verifying ancestry and rechecking the worktree registry. Verify local smoke equals the freshly fetched origin/smoke. Preserve local changes or divergence and report any remaining step.
2. Apply the done and worktree checks above. Only retire the same-repository task branch when the recorded PR head is an ancestor of origin/smoke and each existing task ref still matches that head. Exclude main, smoke, protected, shared and promotion branches, branches used by another worktree or open PR (including as its base), and forks. Preserve ambiguous squash/rebase cases for review.
3. After the worktree is released, delete the exact remote ref with an explicit lease: `git push --force-with-lease=refs/heads/<task>:<merged-PR-head-SHA> origin :refs/heads/<task>`. For the verified local branch use a compare-and-delete against the same SHA (`git update-ref -d refs/heads/<task> <merged-PR-head-SHA>`) after rechecking that it is unoccupied. A changed tip or rejected deletion ends that attempt. An already absent ref is complete. Verify local and remote absence and smoke equality; report any retained ref and reason.


## Potwierdzenie sprzątania dla archiwizacji

Po zakończeniu prac przeprowadź odczyt na tej samej maszynie, na której
znajdowały się worktree lub jednorazowe artefakty. Zapisz w komentarzu issue
wynik zgodnie z sekcją „Potwierdzenie sprzątania przed archiwizacją” w
`docs/controller-deployment-profile.md` repozytorium Agent GitHub Flow.
Jeśli krok jest nierozstrzygnięty, zgłoś `blocked`. Zachowane trwałe środowisko
wymaga jawnej decyzji. Nie wklejaj do publicznej karty ścieżek, nazw prywatnych
plików ani wartości poświadczeń.
