# Rejestracja projektu w kontrolerze

Po przygotowaniu GitHub App, osobistego Projectu i jego Auto-add oraz sprawdzeniu jedynego właściciela statusów agent może dodać jednoznacznie wskazany projekt do istniejącego kontrolera. Nie aktywuj admission ani promocji przed przygotowaniem wymaganych checków, ochrony i odwracalnego planu. Sam zapis konfiguracji nie potwierdza działania flow.

Pomocnik `scripts/register_project.py` jest przeznaczony na istniejący host POSIX, uruchamiany jako root z przejrzanego, root-owned wydania poleceniem `/usr/bin/python3 -I /opt/agent-github-flow-mvp/tools/register_project.py --plan` albo `--apply`. Używa istniejącego `agent-flow`, `/etc/agent-github-flow-mvp/config.json` i usługi `agent-github-flow-mvp.service`. Nie wymaga wartości klucza, PAT ani sekretu webhooka. Towarzyszący `validate_registration.py` korzysta z `current/src` wdrożonego kontrolera wyłącznie jako nieuprzywilejowany użytkownik `agent-flow`; główny proces root nie importuje tego kodu. Pomocnik wymaga izolowanego trybu Pythona oraz plików i katalogów nadrzędnych należących do roota bez zapisu dla grupy i innych użytkowników. Przed użyciem w `/opt/agent-github-flow-mvp/tools/` sprawdź skróty obu pomocników, tożsamość wydania, właściciela, uprawnienia i zgodność z działającą usługą. Nie pobieraj kodu z PR lub niezaufanej gałęzi bezpośrednio jako root.

Na stdin przekaż jeden obiekt JSON z potwierdzonymi `repository_id`, `owner`, `repository`, `project_owner`, `project_number`, `trusted_author_ids` i pięcioma jawnymi wartościami boolean: `status_enabled`, `pr_flow_enabled`, `admission_enabled`, `promotion_enabled`, `dependabot_enabled`. `pr_flow_app_author_id` jest wymagany przy PR flow i musi być zaufanym autorem; włączone admission wymaga `admission_tests` jako listy par `context` i `app_id`. Opcjonalne ustawienia admission są opisane w `docs/pr-admission.md`. Te dane są prywatną konfiguracją, nie zapisuj ich w repozytorium, argumentach procesu ani logach. Użyj istniejącego bezpiecznego kanału SSH i stdin; nie wypisuj JSON-a ani poświadczeń w czacie.

Najpierw uruchom `--plan`; wynik `new` lub `exists` opisuje wyłącznie lokalną konfigurację. Przed `--apply` sprawdź poprawne repozytorium, Project, App, reguły i funkcje, w tym to, czy starszy backlog lub kolejka promocji nie zostaną niespodziewanie przetworzone. Dla `new` helper sprawdza i dopisuje jeden wpis, zatrzymuje istniejącą usługę, zachowuje prywatne kopie konfiguracji i SQLite, używa jej blokady oraz po zapisie atomowym wznawia usługę. Używa stałej granicy dla nowego wpisu i nie przesuwa istniejących granic. Dla `exists` nie zatrzymuje usługi ani nie zapisuje konfiguracji; sprawdź zdrowie usługi osobno. Konflikt, stara granica SQLite, niekompletny stan lub niepewny wynik nie są zgodą na nadpisanie; odczytaj sytuację przed wznowieniem. Nie edytuj ręcznie konfiguracji podczas rejestracji: jej porównanie przed zapisem nie jest atomowym warunkiem wobec niezależnego edytora.

Przy błędzie po zmianie konfiguracji helper próbuje przywrócić tylko dokładnie własny wpisany plik i uruchomić poprzednią usługę. Nigdy nie przywraca starej bazy automatycznie: nowa granica mogła już zostać zapisana. `manual-recovery-required`, utrata połączenia lub przerwanie procesu wymagają sprawdzenia stanu usługi, aktualnej konfiguracji, blokad i granicy SQLite przed kolejną próbą. Gwałtowne przerwanie po zatrzymaniu usługi może pozostawić ją wyłączoną; nie uznawaj samej odpowiedzi `registered` za dowód, że projekt i jego checki działają. Po uruchomieniu sprawdź usługę, kolejkę oraz rzeczywisty przepływ jednej karty i PR zgodnie z `references/mvp-onboarding.md`.
