# Onboarding to the current MVP

First inspect the real repository, its instructions, existing Project, issue and PR workflow, App installation and competing status writers. Do not infer an empty setup from a missing local config or inaccessible API. Run the read-only diagnostic; a known Project can be supplied explicitly as `--project user:OWNER/NUMBER` or `--project organization:OWNER/NUMBER` together with `--live`. A configured local Project remains authoritative if the supplied identity differs. The diagnostic cannot verify the Auto-add filter, central registry, secrets, Project workflow targets or complete ownership.

The central GitHub App sends signed issue and comment events to the Mikrus controller; private configuration selects enrolled repositories and trusted authors. The App reads issues, while a user PAT operates personal Projects. The controller keeps its queue and checkpoint in private SQLite, handles one status writer, and scans after startup and nightly. Do not create or distribute per-project relay credentials for this model. Verify the actual service, registration, permissions, backup and rollout instead of assuming them from code or a saved credential.

For each Project, verify `Auto-add to project` selects the intended repository and issue filter. Inspect competing built-in rules, including item added, item closed, PR linked and auto-close issue; disable only rules that conflict with the agreed owner. GitHub's enabled-workflow names alone do not reveal filters or targets. A UI step may be needed; do not promise unattended setup. Old issues can be added when updated, even though there is no bulk historical import.

For a new project, complete the agreed setup before its first product commit. For an existing one, document the current writers, select a bounded real issue, preserve old credentials and automation until a controlled handover, verify a `[FLOW]` status change and recovery, and distinguish the result from an observed nightly run. Never expose secret values, private mappings or issue content in public repositories or logs. Owner and agent perform smoke together; only the owner decides to close the issue.
