# Onboarding to the current MVP

Use this sequence for a new repository or an existing project's controlled migration. The agent performs the supported setup within the authorized scope; ask the owner only when their authentication, a genuine decision, missing access, or the active tool's policy requires their participation. A checklist or green diagnostic alone is not a completed onboarding.

## 1. Establish the actual starting point

Read applicable repository instructions and inspect the live repository, default and integration branches, open issues and PRs, existing Project, CI, App installation, permissions, and every current status or release writer. Preserve concurrent work and history. Run `scripts/diagnose.mjs --repo <path>`; add `--live` when authorized and supply a known Project as `--project user:OWNER/NUMBER` or `--project organization:OWNER/NUMBER`. A configured local Project remains authoritative if the supplied identity differs. Missing local config or an unavailable API does not prove that a Project or automation is absent.

Compare the local checkout's commit with the live default-branch commit before choosing a base; fetch the remote ref when needed. An existing checkout can be behind while other worktrees contain active work. Start the integration branch from the verified intended remote commit without resetting or switching another session's checkout. If the diagnostic cannot list the default-branch workflow directory, inspect GitHub's Actions workflow list separately: an empty registered list and an unreadable directory are distinct observations, not proof that CI is configured or absent everywhere.

For a new product, complete the applicable setup before the first product commit. GitHub may require an initial infrastructure-only commit to create branches and run setup CI; it must not contain product work. If a prerequisite is blocked, keep the product commit blocked and report the specific missing evidence. For an existing project, agree the migration boundary with the actual owners and use a bounded real issue; do not rewrite history or assume old issues should all receive one status.

## 2. Prepare the Project and access

Reuse the appropriate Project or create one only after checking for an existing backlog. Its single-select Status must distinguish `decision-gate`, `needs-design`, `audit`, `spike`, `agent-ready`, `review`, `smoke` and `done`. New issues enter `needs-design`; closing an issue remains the owner's decision.

For the first Project view, invoke `scripts/onboard.mjs` with the explicit repository and Project and `--apply`. Before changing either, the helper requires the Project's linked-repository list to be readable, complete and to include this repository. During authorized onboarding, after confirming the intended association, add `--link-project` to create a missing link; an ordinary project check does not create one. A missing link alone is not proof of a wrong Project. An uncertain write is re-read rather than blindly repeated; incomplete or changing identity and links block the operation. For an identified brand-new, empty Project only, add `--initialize-empty`: the helper refuses default-state replacement when any active or archived item exists or the state differs from GitHub defaults, preserves the three default option IDs, and re-reads after each write. It sets the first table view to `BOARD_LAYOUT`; if no view exists, it creates the first one. It checks the eight ordered Status options and verifies that board columns group by Status, preserving the existing view filter and name. A prior `BOARD_LAYOUT` with a different grouping, an unsupported layout, a partial read, mismatched statuses or an uncertain write stays blocked; inspect the exact state and use the Project UI where the API cannot set grouping. API grouping and option reads do not prove all individual columns are visible: inspect the actual view and correct hidden columns using the authorized UI before marking the check complete. Do not replace existing Project statuses or silently overwrite conflicting configuration.

Verify that Auto-add selects the intended repository and `is:issue`. Inspect competing rules, including item added, item closed, PR linked and Auto-close issue; disable only conflicting writers. Enabled-workflow names from the API do not reveal filters or target fields. When the supported API cannot set the filter or rule, the agent uses the authorized Project UI: open **Workflows → Auto-add to project**, read the enabled state, repository and filter in viewing mode, and leave a matching rule untouched. If setup is needed, choose **Edit**, select the intended repository, enter `is:issue`, save and enable, then return to viewing mode and read back all three. Preserve existing rules and repositories in a shared Project; if the UI cannot add the desired rule without replacing unrelated configuration, report the conflict instead of overwriting it. Old issues can appear on later updates; do not call Auto-add a historical import. Check other automation and multi-repository limits before switching ownership.

Use the existing centrally installed GitHub App and the central Project credential; do not create a relay token per repository. Check the existing installation before requesting or making an access change: the repository may already be selected. Restrict installation changes to the intended project and retain existing installations. Adding a repository exposes it to the App's existing permissions and may send its subscribed event content to the central endpoint; check the actual scope and follow the active tool's confirmation policy. Check App access and the Project read separately without displaying credential values. If adding a repository or accepting App permissions is unavailable through supported tools, use the authorized installation UI or hand off the exact step. Do not infer access from a saved key or add unrelated repositories.

## 3. Establish one delivery path

Use the project's current `main` and `smoke` or explicitly agreed equivalents. Create missing branches from the verified intended base, without force-pushing or disturbing unrelated work. Add the common issue contract and project instructions, including the current-head review with DA and the owner's smoke/closure decision. Prepare project-owned CI with synthetic data, no product secrets, and checks appropriate to that product.

Record how the project distinguishes its tested source, smoke environment and actual deployed version, or explicitly mark missing evidence as unverified. Choose proportionate project-owned mechanisms; a project without a runtime does not need an invented deployment. Keep test writes isolated with synthetic data, and agree with the owner on a specific scope before using a production-data copy or writing to a real external system.

When integration tests require a database, use a disposable isolated instance and the project's dedicated test database, never an existing product database. Reproduce required application-role restrictions rather than running the tests as a database administrator, and keep any test credentials synthetic. Verify the same setup in hosted CI; a local passing suite alone does not establish Actions behavior.

The `scripts/onboard.mjs` helper is the shared entry point for the currently automated subset. With `--apply --create-smoke`, it creates a missing `smoke` only from a twice-read default-branch head, re-reads it, and never moves an existing branch. An empty repository is reported as requiring an infrastructure-only first commit. Without `--create-smoke`, even `--apply` only checks branch existence. An uncertain write is not retried automatically. The helper always reports `ready: false`, `state: partial`, and exits 2 until the remaining access, workflow, CI, protection, controller and real-handover requirements are actually implemented and verified; neither a successful board nor branch result permits a product commit.

For a new repository without CI, adapt `assets/ci-template.yml` into `.github/workflows/ci.yml`: inspect the actual project stack, add the setup and real test commands it needs, and use isolated synthetic data and services. The template deliberately fails and contains an invalid all-zero action SHA until both are replaced; it is not a working check or permission to claim tests passed. Resolve the reviewed full commit containing `.github/actions/wait-admission` in `OtisRed/agent-github-flow`, verify it exists and pin that SHA. Do not overwrite an existing workflow: inspect and integrate its actual jobs, tests, event triggers and protection instead. Complex projects may need multiple workflows; preserve their existing checks and configure matching retry targets in the controller. Run actionlint and the real project tests, then check the hosted Actions run; if a new product has no tests yet, keep this requirement open rather than inventing a green result.

Before enabling central admission, ensure a PR into `smoke` can run the `verify` job. The admission-enabled path must wait for the App's `flow-admission` result for the current PR head **before** checking out or executing candidate code and expensive tests, using the reviewed, pinned shared action or an equivalent trusted helper; it must not trust a helper supplied by the candidate PR. The action calls the existing shared waiter and requires the numeric App ID, a valid PR SHA and checks read access. The example gates only PRs to `smoke` when `FLOW_ADMISSION_ENABLED` is true; pushes and PRs to other bases still run project tests. Give the workflow the read permissions needed for repository contents and checks, and avoid persisting checkout credentials. Set `FLOW_ADMISSION_APP_ID` and enable `FLOW_ADMISSION_ENABLED` only when the central receiver, CI gate and rollback are ready. Inspect the checked-out AGF version's `docs/pr-admission.md` for the exact integration and recovery procedure. A PR can still modify its workflow or job definition; review those changes and do not claim this template is independent enforcement against its author.

Protect `smoke` with the verified project check and `flow-admission` from their intended GitHub Apps once both paths are ready. Protect `main` with the project check and a PR path; apply protections to administrators, preserve existing compatible rules, and do not require GitHub Approve. Confirm the actual check names and App identities by readback. During bootstrap, any temporary gap or blocked PR must be explicit; never claim a required check exists just because it is configured.

## 4. Register and verify the controller

The central App sends signed events to the Mikrus controller; private configuration maps each enrolled repository to its Project and trusted authors. App tokens handle repository operations, and a user PAT operates personal Projects. The queue and checkpoint are in private SQLite. Keep project mappings, credentials and issue contents out of public files and logs.

Use the existing deployment and its `docs/mvp-service.md`, `docs/pr-admission.md` and `docs/nightly-promotion.md`; verify the deployed version rather than assuming a source commit is live. Before editing private configuration, confirm the exact repository and Project identities, existing owners, service health, queue and recoverable configuration and SQLite backups. Validate a restricted, service-owned candidate before activation. Preserve every unrelated project and the existing enrollment boundary: once registered, do not silently change `enrolled_at` or overwrite a newer live checkpoint from an old backup. Restart only the existing service; check health, errors and queue progress afterward. Keep status, PR handoff, admission and promotion disabled until each one's prerequisites are in place, then verify each enabled flag and its live behavior. Do not run a second controller against another copy of the database.

For a configuration cutover, confirm each stop, guarded replacement and start separately, and verify the running service and actual flags after restart; do not treat the final output of a command batch as proof that every earlier step succeeded. If a step fails, inspect the live service and configuration before resuming or restoring the saved configuration.

Before enabling promotion, inspect the existing closed prefix and what could reach `main`, including changes predating onboarding. Promotion runs centrally during the configured nightly window; an open issue must not be treated as closed. A dry read does not prove a later scheduled promotion or a deployment. In an uncertain write, re-read actual state before retrying; stop if ownership or outcome is ambiguous.

## 5. Prove the handover

Use a real, bounded issue: verify App and Project reads, an observed `[FLOW]` status change, and one clear status owner. Verify a newly created issue reaches the intended Project and `needs-design`; a manually inserted card does not prove Auto-add. For PR flow, verify the current-head review with DA, `flow-admission`, the CI wait and actual project checks, App merge to `smoke`, and the resulting issue status. Record separately what was observed, what was only tested synthetically, and any missing nightly, rollback or new-project evidence.

Leave older backlog cards and product work to their proper owners; record any uncompleted migration as actionable follow-up. Report missing access or a blocked setup honestly. The owner and agent perform smoke together, and only the owner decides whether to close the issue; promotion and deployment remain separate facts.
