# Diagnostic and adoption

Run `node <skill-directory>/scripts/diagnose.mjs --repo <path>` for local inventory; use `--live` for fixed read-only GitHub API probes, subject to network access and applicable local rules. If the Project is known but no supported local config exists, supply `--project user:OWNER/NUMBER` or `--project organization:OWNER/NUMBER`. A conflicting configured identity blocks the Project read; a supplied identity does not prove Project membership or enrollment. A `--live` request does not use a project-specific facade: if local instructions require that facade for the question, use it separately instead. No script may call a repository-provided executable merely to discover configuration.

The JSON result gives `observedAt`, `scope`, `checks`, `inventory` and `limitations`. Every check has `id`, `state`, `evidence`, and `next`. `ok` means only the named observation succeeded; `missing` means an explicitly observed local absence; `conflict` is a concrete conflicting configuration; `unverified` means missing permission, ambiguous identity, unavailable network/tool, malformed data, or a check outside scope. Observed local files are not deployed GitHub configuration. No global pass/fail means readiness.

A complete, error-free live Project read produces `conflict` if its explicitly configured Status field is not a single-select field in that Project. Partial pages, permission failures and ambiguous results remain `unverified`. This does not identify every conflicting owner; inspect Project workflow targets and actual owner definitions before asserting such a conflict.

For one PR, run `node <skill-directory>/scripts/pr-evidence.mjs --repository OWNER/REPO --pr N [--issue N] [--expected-sha SHA]` when live reads are permitted. It makes two bounded read-only GraphQL queries, returns only a compact snapshot (never the PR body), and compares the initial head, last commit, and reread head. `--issue` checks the one-line `Refs #N` target; without it, a single reference is observed but its identity is unverified. `--expected-sha` compares a previously captured full SHA with the reread head. Missing Refs describes the common target convention, not a violation of an existing project's current instructions. A consistent head is point-in-time evidence only; checks, reviewer approval, branch topology, smoke, and readiness remain outside this helper.

The helper discovers Git root, local instruction and workflow files, GitHub remotes without printing credentials, and an existing `.github/workflow/project.json` when it matches the supported Project identity shape. With `--live`, an unambiguous GitHub remote is needed. It reads repository metadata, workflow file names on the default branch, and, when a local or explicitly supplied identity is unambiguous, Project status options and enabled built-in workflow names. Inspect the Auto-add filter and potentially competing status workflows through a supported source or the UI: names alone do not prove configuration. It cannot determine built-in workflow target values or filters through this API, determine token scopes/secret contents, prove all automations have one owner, verify issue/PR contracts, run test suites, or verify full board health. Those remain `unverified`; use local approved tools or UI for targeted inspection. It does not discover arbitrary provider-specific profile formats or infer absence of a Project when local config is absent.

For a new repository, propose the common states, branch model, issue/PR contract, project instructions, tests and CI based on its needs and access. For an existing one, first compare actual project instructions and live state with the target; preserve existing data, identify conflicting writers, plan a controlled handover with rollback and validation, and use appropriate authorization for mutations. Do not assume an empty project from an inaccessible one.
