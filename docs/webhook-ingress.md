# Odłączony model wejścia webhooków

Status: **nie jest uruchomionym odbiornikiem ani kontrolerem**. Issue #77. Moduł `src/webhook_ingress.py` jest modelem przyjmowania metadanych do nowej, prywatnej kolejki na hoście POSIX. Nie tworzy serwera HTTP, nie odczytuje konfiguracji ani sekretów samodzielnie, nie pobiera issue, nie uruchamia workera, nie aktualizuje Projectu i nie zmienia obecnego endpointu spike. Nie migruje bazy spike ani nie zastępuje zatwierdzonego projektu checkpointu na chronionej gałęzi.

## Kontrakt modelu

- `validate_registry` wymaga jawnych, niepowtarzających się par `(installation_id, repository_id)` i nie dopuszcza jednej tożsamości repo pod dwiema instalacjami. Zaufanie i źródło tej listy muszą zapewnić przyszłe uruchomienie; model nie wykonuje onboardingu.
- `initialize` tworzy nową bazę w prywatnym katalogu albo otwiera wyłącznie bazę z właściwym `application_id`, wersją, dokładnym schematem i przypiętym kluczem fingerprintu. Nieznane obiekty, w tym triggery, są odrzucane; ponowna kontrola odbywa się pod blokadą transakcji przed zapisem. Marker klucza nie dowodzi świeżości ani pochodzenia bazy: stara kopia z poprawnym kluczem może przejść ten test. Innej bazy nie migruje, ale otwarcie bazy może uruchomić odzyskiwanie SQLite z dziennika jeszcze przed weryfikacją jej tożsamości. Dlatego brak migracji nie oznacza gwarancji nienaruszenia obcego pliku: integracja musi zapewnić zaufaną ścieżkę i zaprojektować procedurę odzyskiwania. Pliki i katalog muszą należeć do procesu i nie mogą być dostępne innym użytkownikom; dowiązania symboliczne nie są przyjmowane. Ścieżkę, własność i uprawnienia integracji z systemd trzeba jeszcze osobno zaprojektować i sprawdzić.
- `receive` sprawdza kształt identyfikatora dostawy, wielkość body i podpis HMAC-SHA256, następnie dopuszczone działania `issues` i `issue_comment` oraz tożsamość repozytorium i instalacji. Znane nieistotne działania issue, komentarze PR oraz podpisany ping mogą zostać jawnie pominięte bez dodania pracy; niepełna tożsamość nie jest przyjmowana. Zdarzenia instalacji App, istotne dla dostępu, zwracają `attention`, a nie ciche zignorowanie; wymagają osobnego właściciela obsługi. Nagłówki event i delivery nie są objęte podpisem GitHuba.
- Zapisywane są tylko ID istniejącej dostawy, instalacji, repozytorium, numer issue, opcjonalnie ID komentarza, dozwolony typ i działanie, fingerprint HMAC body oraz czas odbioru. Fingerprint używa odrębnego, stabilnego klucza o wysokiej entropii, a nie sekretu webhooka: dlatego rotacja sekretu webhooka nie powoduje fałszywego konfliktu ponowionej dostawy. Sposób bezpiecznego utworzenia, przechowywania, kopii i rotacji tego klucza nie został wdrożony; możliwe współdzielenie materiału źródłowego z istniejącym kluczem wymaga odrębnego projektu i bezpiecznej separacji celów. Nie zapisuje się body issue ani komentarza. Metadane prywatnych projektów, podpis oraz baza są danymi prywatnymi.
- Model wymaga `journal_mode=DELETE` i `synchronous=EXTRA`; istniejąca baza w innym trybie jest odrzucana, bez automatycznego przełączenia. W testowym runtime Mikrusa Python zgłasza SQLite 3.45.1; rzadki [błąd WAL-reset](https://www.sqlite.org/wal.html#the_wal_reset_bug) w części starszych SQLite wymaga sprawdzenia aktualizacji dystrybucyjnej przed jakimkolwiek produkcyjnym użyciem WAL. DELETE + EXTRA ogranicza ten konkretny problem w modelu, nie jest dowodem odporności na awarię sprzętu. [SQLite opisuje gwarancje synchronizacji](https://www.sqlite.org/pragma.html#pragma_synchronous). `accepted` oznacza zatwierdzony transakcyjnie zapis; `duplicate` oznacza tę samą dostawę z tym samym body i tożsamością. Te dwa wyniki mogą w przyszłości zostać zmapowane na odpowiedź 2xx; `ignored` również wymaga jawnej polityki mapowania 2xx i monitoringu. Ten sam ID dostawy z odmiennymi metadanymi lub treścią body daje `conflict`; nieznana para projektu i instalacji daje `unknown_project`; błędy konfiguracji i bazy, nieprawidłowy podpis i nieobsługiwane zdarzenia są osobnymi wynikami. Podpis weryfikowany jest niezależnie przed rozpoznaniem duplikatu. Żaden z tych wyników błędu nie jest potwierdzeniem przyjęcia do kolejki.
- Takie samo podpisane body pod innym ID jest zapisywane osobno. Może to być zarówno poprawna odrębna dostawa, jak i replay, ponieważ nagłówek ID nie jest podpisany. Model nie zapewnia exactly-once. Przed jakąkolwiek zmianą statusu przyszły pojedynczy wykonawca musi osobno sprawdzić aktualny stan GitHuba, uprawnienia i checkpoint, a system musi ograniczać nadużycia i powtórzenia.

## Granice i dalsza praca

Testy używają wyłącznie syntetycznych danych i tymczasowych baz. Obejmują kilka projektów, ponowienia i konflikt, identyczne body pod innymi ID, odmowę nieznanego projektu i złego podpisu, odczyt w osobnym procesie, błąd magazynu, odmowę obcej bazy, obcego schematu, zmienionego trybu dziennika i niebezpiecznych uprawnień; obejmują też współbieżne zapisy, blokadę bazy oraz rotację sekretu webhooka przy zachowaniu klucza fingerprintu. Nie są próbą prawdziwego GitHub webhooka ani awarii zasilania. Test odczytu w osobnym procesie nie jest pełnym restartem hosta.

Kolejka przyjęć jest osobna od checkpointów `[FLOW]`. W tym etapie nie ma usuwania/przetwarzania wpisów, schematu uzgodnionego workera, polityki retencji, alarmowania, kopii, rotacji klucza fingerprintu, odzyskiwania po rollbacku bazy ani ochrony przed powodzią replay. GitHub nie ponawia błędnych dostaw automatycznie. Przed wdrożeniem trzeba połączyć i przetestować HTTP, limitowanie, zaufaną rejestrację, jeden globalny worker, autoryzowane odczyty GitHub, walidację przekazań, statusy i odtwarzanie. Adapter HTTP musi też jawnie obsłużyć i monitorować nieobsługiwane obecnie zdarzenie `github_app_authorization`, zamiast po cichu potwierdzać je kodem 2xx.

Uruchomienie testów na POSIX: `python3 -m unittest discover -s tests -p 'test_webhook_ingress.py' -v`.
