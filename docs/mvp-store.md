# Prywatny magazyn MVP

`src/mvp_store.py`, `src/mvp_intake.py` i `src/mvp_http.py` są przygotowywanymi elementami kontrolera #81. Adapter HTTP nasłuchuje tylko na lokalnym interfejsie, ale nie ma jeszcze uruchamianej usługi; kod nie czyta GitHuba, nie zmienia statusów i nie jest wdrożony na Mikrusie.

Jedna baza SQLite przechowuje numer wersji pracy dla każdego repozytorium i issue, ostatnią ukończoną wersję, ID i skrót ostatniego zaakceptowanego komentarza oraz czas i cel niepewnego zapisu statusu. Odbiornik sprawdza podpis i dozwoloną instalację oraz repozytorium, a następnie zapisuje wyłącznie sygnał; odpowiedź `accepted` powstaje po zatwierdzeniu transakcji. Wiele sygnałów można połączyć w jeden odczyt. Kolejna wersja, która powstanie podczas pracy, pozostaje do ponownego sprawdzenia również po restarcie. Powtórny webhook może wywołać dodatkowy odczyt i nie jest traktowany jako dowód zmiany GitHuba.

Błąd można przypisać do sprawdzanej wersji issue jako krótki kod, aby nie zatrzymywał innych zadań. Nowszy sygnał budzi ponowną próbę, a błąd pozostaje widoczny do skutecznego zakończenia. Monitoring i sposób prezentowania tych błędów trzeba jeszcze wdrożyć.

Przed żądaniem zmiany statusu wykonawca zapisuje jego cel, czas i wersję pracy oraz ID i skrót komentarza, który uzasadniał tę operację. Dzięki temu po restarcie można odróżnić jej podstawę od nowszego przekazania. Przy niepewnym wyniku worker czeka co najmniej 120 sekund, a następnie ponownie odczytuje GitHub i weryfikuje komentarz; pozostałe zadania mogą być w tym czasie obsługiwane. Jeśli cel jest widoczny, magazyn zachowuje checkpoint przed skasowaniem informacji o niepewności w tej samej transakcji. To nie usuwa zaakceptowanego ryzyka wyjątkowo późnej realizacji starego żądania. Sam magazyn nie sprawdza prawdziwości odczytu, autora komentarza, jego skrótu ani porządku reopen — robi to kontroler przed ukończeniem pracy.

Bazę tworzy się wyłącznie podczas jawnej inicjalizacji. Zwykłe otwarcie nigdy nie tworzy brakującego pliku; obca lub niedokończona baza jest odrzucana. Katalog i plik należy zabezpieczyć jako prywatne. Nadal trzeba przygotować i sprawdzić kopię oraz kontrolowane odzyskanie: samo przywrócenie starszego pliku nie dowodzi kompletności checkpointów. Jeden zaufany worker jest założeniem, które przyszła usługa musi wymusić. Inicjalizacja, dostęp do pliku, kopie, monitoring, odczyt danych, uruchomienie HTTP za istniejącym proxy i integracja z workerem pozostają do wykonania przed wdrożeniem.
