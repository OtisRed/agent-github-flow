# Projekt odzyskiwania przekazań FLOW

> **Zmiana decyzji właściciela, 3.11.2026:** checkpoint ma trafić do osobnej
> technicznej gałęzi każdego repozytorium. Opisany niżej zapis znacznika do
> treści issue jest historycznym modelem: `updateIssue` może nadpisać
> równoczesną edycję kontraktu. Nie uruchamiać tego writera. Nowy wariant
> wymaga jeszcze zaprojektowania i sprawdzenia, w tym warunkowego zapisu,
> ochrony gałęzi, odtwarzania oraz wyścigów statusu Projectu.

To projekt i izolowany model decyzji, a nie działający kontroler. Stosują go docelowo zarówno reakcja na komentarz (#5), jak i nocna kontrola (#6). Jeden kontroler odpowiada za zapis danej karty; migracja nie uruchamia równoległego właściciela VSone.

## Znacznik i dowody

W technicznym fragmencie treści issue przechowujemy wersję schematu, fazę `pending` albo `committed`, istniejące ID komentarza GitHuba jako ciąg cyfr, SHA-256 jego dokładnej treści UTF-8, poprzedni status karty i status docelowy. ID nie jest nowym identyfikatorem operacji. Przykładowy model danych:

```json
{"version":1,"phase":"pending","commentId":"123","digest":"<sha256>","fromStatus":"agent-ready","targetStatus":"review"}
```

Lokalny adapter `src/flow-marker.mjs` obsługuje jeden blok `<!-- agent-github-flow:state` ... `agent-github-flow:state -->`, którego środkowy wiersz zawiera kanoniczny JSON bez dodatkowych pól. Nieprawidłowy, powielony lub inaczej sformatowany blok blokuje zmianę. Adapter zachowuje pozostałą treść dokładnie, a przy zastępowaniu wymaga oczekiwanego poprzedniego znacznika. Dodanie do treści bez znacznika wymaga jawnego `expected: null`; samo to nie uprawnia do inicjalizacji na GitHubie. Adapter operuje na przekazanym tekście i nie zapisuje issue.

Integracja zapisu do GitHuba i obsługa współbieżnych edycji pozostają do implementacji i testów. Nie wolno zastąpić treści issue starym snapshotem: przed zapisem konieczny jest ponowny odczyt i zachowanie reszty treści. Sam ponowny odczyt nie jest operacją atomową i nie daje gwarancji braku wyścigu. Format delimitera używa LF; zachowanie rzeczywistego API wobec zakończeń wierszy trzeba sprawdzić przed wdrożeniem.

Komentarz musi istnieć, mieć dokładnie ten sam ID i treść odpowiadającą zapisanemu skrótowi, być poprawnym `[FLOW]` oraz pochodzić od zaufanej tożsamości GitHuba. Przed wyborem komentarza trzeba odczytać wszystkie strony danych oraz rozstrzygnąć nowsze wpisy. Nowszy wadliwy wpis zaufanego autora nie pozwala po cichu zastosować starszego. Deklarowane pole `Rola` nie jest dowodem tożsamości. SHA-256 wykrywa zmianę obecnej treści; nie dowodzi, że komentarz nigdy nie został edytowany i przywrócony.

`src/flow-handoff.mjs` wybiera najnowszy komentarz zaufanego autora spośród przekazanych danych, identyfikując autorów po stabilnym node ID. Późniejszy wpis osoby spoza listy jest pomijany; brak tożsamości autora, brak pełnego odczytu, identyczny czas najnowszych zaufanych komentarzy lub wadliwy ostatni zaufany wpis blokują wybór. Widoczna edycja ostatniego wpisu również zatrzymuje automat do wyjaśnienia, bez ustanawiania zakazu edytowania komentarzy. Brak widocznej daty edycji nie jest dowodem, że historii edycji nie usunięto. Kod nie pobiera stron ani nie potwierdza ich kompletności, tożsamości lub istnienia wcześniejszego znacznika. Potrzebuje obu identyfikatorów tego samego komentarza: dokładnego numerycznego ciągu cyfr do znacznika oraz osobnego node ID do czytnika GraphQL. Wynik `handoff` nie jest zgodą na zapis — wymaga jeszcze weryfikacji znacznika, epoki oraz świeżego odczytu.

Przy pierwszym przekazaniu, gdy zarówno znacznik issue, jak i checkpoint Projectu są puste, czytnik może użyć jawnego, stałego czasu `cutoverAt`. Komentarze utworzone w tej samej sekundzie lub wcześniej pozostają w sprawdzanej historii, ale nie są kandydatami do inicjalizacji. Nowy wadliwy komentarz nadal blokuje wybór; nie wolno cofnąć się do starszego. Po istnieniu checkpointu tego filtra się nie stosuje: wcześniejsze potwierdzone przekazanie musi pozostać dostępne do weryfikacji. Niepoprawna granica blokuje wybór, a brak znacznika i checkpointu sam w sobie nie dowodzi, że oba zapisy nie zostały wcześniej usunięte. Faktyczny czas migracji musi być ustalony i chroniony w konfiguracji; testowe daty nie aktywują automatu.

`src/flow-handoff-reader.mjs` pobiera komentarze z GraphQL po 100 na stronę, mapuje `fullDatabaseId` jako dokładny ciąg cyfr, node ID oraz identyfikator autora typu `User` lub `Bot` z tego samego rekordu. Wymaga jawnej listy zaufanych node ID od wywołującego; brak wymaganych danych blokuje odczyt. Sprawdza liczbę komentarzy oraz ponownie pobiera i porównuje każdą stronę, odmawiając przy wykrytej zmianie. Obowiązuje limit 100 stron i 8 milionów znaków snapshotów. Wynik `evidence` jest jedynie dowodem odczytu, a wewnętrzny `handoff` może również mieć wartość `absent`: taki wynik nigdy nie ustawia statusu. Dwukrotny odczyt nie jest atomowym snapshotem ani nie chroni przed późniejszą zmianą, a sam czytnik nie ustala pochodzenia znacznika ani nie wykonuje operacji zapisu. Odczytowa próba dla #4 odczytała pięć komentarzy i wybrała `done`, a dla #5 jeden i `needs-design`; wielostronicowość sprawdzono na danych testowych, nie na żywym API.

Sama poprawna składnia znacznika w body nie dowodzi, kto go zapisał. Użytkownik lub inna osoba z prawem edycji issue mogłaby podmienić go na inny poprawny blok. Przed wdrożeniem trzeba wybrać i sprawdzić wiarygodny sposób potwierdzenia pochodzenia znacznika albo wykazać odpowiednią granicę zaufania dla wszystkich uprawnionych edytorów. Brak takiego dowodu blokuje sterownik; weryfikacja autora komentarza tego nie zastępuje.

Historia edycji może pomóc w diagnostyce, lecz API opisuje pole `diff` jako podsumowanie zmian; same metadane edytora nie wiążą obecnego bloku z konkretną kompletną edycją. Rekordy edycji mogą być usunięte. Ewentualny podpis znacznika też wymaga analizy: sam podpis historycznie poprawnej wartości nie wyklucza jej późniejszego odtworzenia. Integracja musi rozstrzygnąć zarówno pochodzenie, jak i wykrywanie cofnięcia do starszej wartości.

### Wariant do dalszego sprawdzenia: zaufani edytorzy issue

Bez dokładania nowego sekretu można oprzeć bezpieczeństwo na zaufanej, weryfikowanej granicy edycji całego issue. [GitHub dopuszcza edycję issue m.in. jego autora](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/editing-an-issue), więc w publicznym repozytorium samo sprawdzenie współpracowników repo nie wystarczy. Kandydat do wdrożenia musiałby sprawdzać stabilną tożsamość autora issue, osoby i zespoły z uprawnieniem edycji oraz wszystkie aplikacje z takim dostępem; wszystkie te tożsamości musiałyby należeć do jawnie przyjętej listy, ponownie sprawdzanej przed działaniem. Niedostępny lub niepełny odczyt uprawnień oznacza blokadę.

To model zaufania do uprawnionych edytorów, a nie kryptograficzny dowód autora konkretnego znacznika ani zabezpieczenie przed omyłkowym cofnięciem jego prawidłowej starszej wartości. Zapis w body wciąż wymaga procedury inicjalizacji, ochrony przed współbieżną edycją oraz rozwiązania problemu cofnięcia. Alternatywą jest niezależny trwały punkt odniesienia z ochroną przed cofnięciem; sam podpis znacznika nie wystarczy. Żaden z tych wariantów nie jest jeszcze wdrożony.

Odczyt współpracowników aktualnego repo wskazał konto właściciela jako administratora. Lista instalacji GitHub Apps widoczna w ustawieniach konta potwierdziła kilka aplikacji z prawem zapisu issue w tym repozytorium. Odczyt `/user/installations` bieżącą tożsamością zwrócił HTTP 403 wymagający innego rodzaju tokenu. Te obserwacje nie stanowią kompletnej listy wszystkich tokenów i mechanizmów mogących edytować issue; wariant automatycznej weryfikacji granicy zaufania pozostaje nieweryfikowany.

### Badany wariant: punkt odniesienia na karcie Projectu

Kandydatem jest dodatkowe techniczne pole tekstowe na tej samej karcie Projectu. Przechowywałoby bieżący znacznik oraz podczas `pending` poprzedni zatwierdzony znacznik. Odnosi się ono nadal do istniejących ID komentarzy, nie wprowadza identyfikatora operacji ani nowego sekretu: do odczytu i zapisu używałoby obecnego PAT użytkownika Projectu. Znacznik w treści issue pozostaje zgodnie z wcześniejszą decyzją. GitHub wspiera [aktualizację pola tekstowego Projectu](https://docs.github.com/en/graphql/reference/projects#updateprojectv2itemfieldvalue), ale obecna tablica nie ma takiego pola, a długość, konfigurację i zachowanie rzeczywistego API trzeba sprawdzić osobno.

Odrębny, prywatny Project testowy z syntetyczną kartą potwierdził zapis i dokładny odczyt wartości `pending` (400 znaków) i `committed` (220 znaków) w polu tekstowym przez uwierzytelnione CLI użytkownika. Status karty pozostał niezmieniony, a tablicę testową po zweryfikowaniu zawartości usunięto. Test nie dowodzi maksymalnej długości pola, działania PAT w GitHub Actions, zapisu do issue ani recovery po błędzie sieci; produkcyjnego Projectu nie zmieniano.

Następnie [sonda w GitHub Actions](https://github.com/OtisRed/agent-github-flow/actions/runs/41418861816) użyła istniejącego PAT z testowego środowiska `pat-probe` na kolejnej prywatnej tablicy i syntetycznej karcie. Potwierdziła kolejno dokładny odczyt `pending` i `committed` oraz niezmieniony status; osobny odczyt użytkownika potwierdził końcową wartość. Tablicę testową usunięto po zweryfikowaniu jej zawartości. [PR sondy #26](https://github.com/OtisRed/agent-github-flow/pull/26) przeszedł niezależny przegląd subagenta, a wymóg formalnego GitHub Approve na docelowej gałęzi testowej dostosowano do wspólnego procesu, pozostawiając wymóg PR i egzekwowanie wobec administratora. Współbieżnie uruchomiony wcześniejszy workflow odczytowy zakończył się znanym brakiem mapowania sekretu; nie wykonywał zapisu. Ta próba nie sprawdza zapisu issue, maksymalnej długości pola, rzeczywistego recovery ani produkcyjnego środowiska.

Badany porządek przy przejściu z A do B: najpierw zapisz w polu Projectu `pending B` wraz z poprzednim `committed A` i odczytaj; potem zapisz i odczytaj `pending B` w issue; następnie ustaw i odczytaj status; na końcu potwierdź B w Project i w issue z osobnymi odczytami. Zgodna para `committed B` pozwala dopiero oceniać późniejszy mismatch statusu. Brak lub uszkodzenie któregoś rekordu, zmiana/usunięcie odpowiednich komentarzy, niezgodna epoka, nieoczekiwany status czy niepewna własność zapisu blokują decyzję. Zasady inicjalizacji opisano niżej; pozostają modelem, nie uruchomionym automatem.

`src/flow-witness.mjs` modeluje ten porządek wyłącznie na przekazanym snapshotcie. Dopuszcza wznowienie określonych stanów częściowego zapisu pod warunkiem rzeczywiście potwierdzonej kompletności danych, źródła pola Projectu, jednego właściciela, aktualnej epoki i komentarzy. Są to wymagania wobec przyszłej integracji, a nie właściwości dowiedzione przez ten model. Nie zapisuje ani nie odczytuje GitHuba.

Każdy plan zmiany zawiera kopię spodziewanego checkpointu, znacznika, stanu issue, statusu i danych identyfikujących komentarz. Wykonawca musi pobrać całość ponownie i wyliczyć plan od nowa bezpośrednio przed każdą mutacją; rozbieżność blokuje zapis. Nie jest to atomowy compare-and-swap. W zwykłym przejściu `pending` poprzedni znacznik musi należeć do tej samej potwierdzonej epoki; ponowne otwarcie ma osobny model opisany poniżej.

Pola w issue i Project to dwa miejsca zapisu, ale nie transakcja ani kryptograficzny dowód autora. Project i issue mogą zmienić się między odczytem a zapisem; PAT właściciela nie odróżnia automatu od ręcznej edycji tym samym kontem. Cofnięcie obu zapisów do zgodnej starszej pary nie zostanie wykryte bez dodatkowego, niezależnego punktu odniesienia. Dlatego wariant opisuje odzyskiwanie przy założeniu jednego zaufanego właściciela i nie zastępuje analizy równoczesnych zmian, bezpiecznego bootstrapu, uprawnień, readbacku ani wspólnego smoke. Nie jest jeszcze wdrożony.

Istotna blokada wdrożenia: `updateIssue` zapisuje całą treść bez warunku wersji. Równoczesna edycja kontraktu po ostatnim odczycie może zostać nadpisana przez zapis znacznika, a późniejszy readback tego nie wykryje. Nie włączać zapisu do issue przed rozstrzygnięciem bezpiecznego miejsca i sposobu przechowywania checkpointu. Serializacja samych automatów nie blokuje edycji użytkownika lub innej aplikacji.

Jeśli komentarz zniknął lub zmienił się, dane są niekompletne, źródło nie jest zaufane, karta jest niejednoznaczna albo występuje sprzeczność — nie zapisujemy statusu. Brak znacznika wymaga osobnego bezpiecznego uruchomienia początkowego i nie pozwala zakładać, że wcześniejszych komentarzy nigdy nie usunięto. Podobnie nie da się wykryć komentarza usuniętego, zanim kontroler zdążył go kiedykolwiek zaobserwować i utrwalić jego ID.

Ponowne otwarcie issue rozpoczyna nową epokę pracy: przekazanie sprzed ostatniego zamknięcia lub otwarcia nie może przywrócić historycznego statusu. Integracja musi wiarygodnie ustalić tę granicę na podstawie kompletnej historii stanu natywnego albo jawnego checkpointu #9. Gdy tego nie potrafi, blokuje zarówno zastosowanie znacznika, jak i naprawę mismatch. Właściciel natywnego reentry i kontroler FLOW muszą uzgodnić kolejność unieważnienia starego znacznika i ustawienia nowego statusu.

Jeśli świeży handoff dotrze przed sygnałem `reopened`, a nie istnieją jeszcze checkpointy, model odczytuje czas i kotwicę rzeczywistego reopen. Reopen po `cutoverAt` wymaga najpierw reentry i blokuje bootstrap; reopen sprzed lub w chwili granicy pozostaje historią i nie wymusza resetu. Brak lub niezgodność dowodu blokuje decyzję. Dodatkowy odczyt pełnej historii ma koszt, który trzeba zmierzyć przed produkcyjnym uruchomieniem.

GitHub GraphQL udostępnia [historię edycji treści issue i zdarzenia jego osi czasu](https://docs.github.com/en/graphql/reference/issues) oraz [metadane edycji](https://docs.github.com/en/graphql/reference/users#usercontentedit). Odczyt issue #5 potwierdził dostępność tych pól dla aktualnej tożsamości, ale nie potwierdził kompletności danych we wszystkich repozytoriach ani wiarygodnego dowodu pochodzenia znacznika.

`src/flow-epoch.mjs` sprawdza przekazany, kompletny i uporządkowany ciąg zdarzeń `CLOSED`/`REOPENED`: czy zgadza się z obecnym stanem, czy nie zawiera duplikatów i czy komentarz powstał po ostatnim ponownym otwarciu. Jeśli czasy są identyczne i nie da się ustalić kolejności, odmawia decyzji. Czytnik musi rzeczywiście pobrać wszystkie strony, związać czas z wybranym komentarzem oraz zadbać o wiarygodny moment odczytu. Funkcja nie uzyskuje tych dowodów sama i nie usuwa wyścigu z późniejszym zamknięciem lub otwarciem.

`src/flow-epoch-reader.mjs` jest odczytowym kolektorem dla dostarczonej funkcji GraphQL. Pobiera maksymalnie 100 stron zdarzeń, sprawdza ich liczbę, powiązanie komentarza z issue, zgodność metadanych między stronami i ponownie odczytuje pierwszą stronę. Dowód wskazuje issue, oba ID, czas i skrót konkretnego komentarza oraz kotwicę epoki. Jest jedynie pomocniczą oceną na podstawie otrzymanych danych: nie potwierdza trwałej kompletności historii, pochodzenia znacznika, zaufania do komentarza ani braku równoczesnych zmian po odczycie; nie jest samodzielnym zezwoleniem na zapis. Kontrolowany odczyt rzeczywistego API dla zamkniętego #4 odmówił obsługi zamkniętego issue; dla otwartego #5 zwrócił dowód epoki początkowej i brak eventów. To nie jest test mutacji, reopen ani wielostronicowej historii na żywym API.

## Inicjalizacja i ponowne otwarcie — model do integracji

Przy pierwszej konfiguracji proponowana jest stała, zapisana dla projektu data UTC `cutoverAt`. Gdy brak obu zapisów albo po reopen jest gotowy sentinel, brak komentarza oznacza oczekiwanie. Komentarz nie późniejszy niż cutover nie inicjuje flow; pierwszy poprawny, zaufany komentarz późniejszy niż cutover może zostać przejęty zarówno przez obsługę zdarzenia, jak i przez nocne uzgadnianie po pominiętym zdarzeniu. Konfiguracja tej daty i produkcyjny kontroler nie są jeszcze zaimplementowane.

`src/flow-bootstrap.mjs` modeluje kolejno: zapis tymczasowego checkpointu v2 w Project, znacznika `pending` w issue, ewentualną zmianę statusu, potwierdzenie w Project i issue oraz normalizację checkpointu do v1. Wymaga dowodu związanego z dokładnym komentarzem i epoką; poprzedni zapis po reopen pozostaje w checkpointcie aż do zakończenia inicjalizacji. Przerwanie obsługuje kolejny świeżo wyliczony krok, a nie ślepe ponowienie zapisu.

`src/flow-reentry.mjs` modeluje właściciela reopen (#9): po potwierdzeniu pełnej historii natywnej i najnowszego `ReopenedEvent` zapisuje w Project tymczasowy sentinel, ustawia `needs-design`, usuwa tylko oczekiwany stary znacznik i oznacza sentinel jako gotowy. Kotwica to istniejący ID zdarzenia GitHuba. Kolejny przebieg z tą samą kotwicą nie resetuje postępu. Kolejne reopen może zastąpić zakończony lub jednoznacznie przerwany sentinel nowym, po weryfikacji starego komentarza i stanu pośredniego, lecz nie wykonuje kroków starej epoki. Jeśli zachowany poprzedni komentarz zniknie lub się zmieni, model blokuje działanie. Reopen podczas niedokończonego bootstrapu nadal blokuje się i wymaga osobnego rozwiązania. Czytnik historii i poszczególne kroki sprawdzono na fixture, lecz nie ma jeszcze produkcyjnego kontrolera.

Reopen musi być późniejsze niż stały `cutoverAt`: zdarzenie wcześniejsze albo z tej samej sekundy nie może cofnąć pracy rozpoczętej przed migracją. Dowód natywnej historii zawiera czas konkretnego zdarzenia, a sentinel reentry v3 zachowuje `cutoverAt` wraz z jego istniejącą kotwicą. Zmiana granicy podczas wznowienia albo readbacku blokuje kolejne kroki. Bez poprzedniego checkpointu historyczne komentarze sprzed cutover nie blokują reentry; po zakończonym reentry bez nowego przekazania model oczekuje pracy. Stary eksperymentalny sentinel v2 nie zawiera granicy i jest odrzucany, nie migrowany automatycznie; wcześniejsze próby v2 pozostają dowodami historycznymi. Nie ustala to samoistnie produkcyjnej daty ani nie dowodzi, że checkpoint nigdy wcześniej nie został usunięty.

Po każdym kroku reentry porównywany jest także aktualny handoff. Jeżeli nowe przekazanie pojawi się w trakcie zapisu, readback zwraca konflikt i nie wykonuje kolejnego kroku; poprzedni zapis mógł już jednak nastąpić i wymaga świeżego rozpoznania, a nie ślepego ponowienia. Nie zapewnia to ochrony przed zmianą po końcowym odczycie.

`src/flow-next-handoff.mjs` i `src/flow-transition-runner.mjs` modelują kolejne przekazanie w historycznym wariancie checkpointów w issue i Project. Ich dawny adapter jest fixture testowym, a cały ten wariant wymaga zastąpienia lub odłączenia przed uruchomieniem kontrolera. Wspólny smoke z użytkownikiem i jego decyzja o zamknięciu issue pozostają osobnymi etapami; nie wymagamy formalnego GitHub Approve.

### Izolowana próba inicjalizacji przez GitHub API

`src/flow-github-project.mjs` odczytuje konkretną kartę, powiązane issue i wskazane pola Projectu; stronicuje i dwukrotnie sprawdza karty issue oraz ponownie odczytuje dane karty. Odmawia m.in. dla zarchiwizowanej lub niejednoznacznej karty, niewłaściwego repozytorium i pól, niespójnych danych czy wadliwego checkpointu. Nie nadaje uprawnień ani nie potwierdza pochodzenia danych.

`src/flow-bootstrap-runner.mjs` modeluje co najwyżej jeden krok w starszym modelu. Jego dawny adapter zapisu przeniesiono do `test-support/legacy-flow-github-write.mjs` wyłącznie jako fixture historycznych testów; nie wolno łączyć go z rzeczywistym GitHubem. Zapisywał on opis issue i pole Projectu, co zostało zastąpione decyzją o gałęzi technicznej. Także te historyczne runnery wymagają zastąpienia lub odłączenia przed uruchomieniem kontrolera. Odczyty i zapis nie są transakcją.

`src/flow-snapshot.mjs` łączy odczyt karty, komentarzy i dowodów epoki oraz ponownie sprawdza kartę na końcu. Wynik celowo nie przyznaje zaufania autorom, źródłu checkpointu ani wyłączności pisania — odpowiednie flagi pozostają `false`. `createFlowSnapshotReader` przekazuje opcje osobnego readbacku poprzedniego komentarza, dzięki czemu po normalizacji bieżący snapshot opisuje już nowy checkpoint, a dowód poprzedniego komentarza jest sprawdzany osobno. To nadal odczytowy komponent, nie rozstrzygnięcie polityki dostępu i jednego writera.

`src/flow-cycle.mjs` łączy kroki dla jednego issue w ograniczony przebieg. Wybiera inicjalizację, kolejne przekazanie albo osobny tryb reentry, a niepewnego zapisu nie ponawia. Niedokończone reentry blokuje zwykły handoff do czasu obsługi natywnego stanu. Limit kroków powoduje jawną blokadę i wymaga nowego odczytu przy wznowieniu. Koordynator nie ustanawia polityki zaufania ani nie serializuje różnych uruchomień; te warunki musi zapewnić przyszły kontroler. Liczbę odczytów i koszt API trzeba zmierzyć i ewentualnie ograniczyć bez usuwania wymaganych kontroli.

### Dwie tożsamości dla prywatnego repozytorium

W [odczytowej próbie PAT w Actions](https://github.com/OtisRed/agent-github-flow/actions/runs/41435725290) token potwierdził osobisty Project, konfigurację pól oraz metadane karty. Ten sam PAT nie potwierdził prywatnego issue ani `content` karty przez GraphQL, lecz REST poprawnie potwierdził powiązanie tej karty z tym samym issue. Run zakończył się błędem, ponieważ sonda celowo sprawdzała także niedostępny wariant GraphQL. Nie odczytywano ani nie wypisywano wartości poświadczenia. Wynik dotyczy tego testowego PAT i fixture, a nie wszystkich możliwych zakresów tokenów.

`src/flow-github-split-project.mjs` rozdziela odczyt: PAT dostarcza dane pól Projectu, App dane issue, a REST Projectu z PAT weryfikuje powiązanie karty i issue. Właściciel repozytorium i właściciel osobistego Projectu są osobnymi parametrami. `src/flow-project-rest.mjs` konstruuje wyłącznie adres API GitHuba, pobiera stronicowane dane i używa z `Link` tylko sprawdzonego kursora; kolektor ponawia wszystkie strony i odrzuca duplikaty oraz niejednoznaczność. Dawny `createSplitWriteTransport` pozostaje wyłącznie w historycznej fixture i nie jest częścią docelowego zapisu. Złożony czytnik nadal nie przyznaje zaufania ani wyłączności zapisów.

Składnię i całą ścieżkę odczytową GraphQL/REST sprawdzono na prywatnej fixture przez jedną tożsamość CLI. Osobna [sonda Actions na VSone](https://github.com/OtisRed/agent-github-flow/actions/runs/41437686026) potwierdziła odczyt prawdziwego osobistego Projectu i powiązania jednej karty z issue przez PAT oraz odczyt tego samego prywatnego issue przez token App ograniczony do jednego repozytorium i `issues:read`. Ta sonda nie zapisywała danych i nie uruchamiała złożonego czytnika. Osobną próbę tego czytnika dwoma poświadczeniami opisano niżej; próby kontrolera zapisującego pozostają wymagane przed wdrożeniem. Nie należy poszerzać zakresu PAT tylko na podstawie braku `content` w GraphQL.

`runReadOnlyFlowPreflight` łączy złożony czytnik rozdzielonych tożsamości z ograniczonym przebiegiem koordynatora. Dopuszcza wyłącznie znane zapytania GraphQL, nie przyjmuje writerów ani flag zaufania i ma prywatną blokadę zapisu. Same podane transporty muszą być zaufanymi implementacjami odczytowymi: callback może wykonać inne działania poza kontrolą tego modułu. Próba CLI na jednej syntetycznej karcie wykonała rzeczywiste odczyty i zatrzymała się na `unverified-snapshot` bez zapisu. Użyto jednej tożsamości CLI dla obu transportów; nie jest to próba obu poświadczeń ani docelowego kontrolera w Actions. Przyznanie zaufania i potwierdzenie wyłącznego właściciela pozostają poza preflightem.

`createFlowReadTransports` dostarcza transporty odczytu rozdzielające poświadczenia Projectu i App, ograniczone do znanych zapytań i adresów API GitHuba. Nie wykonują ponowień ani przekierowań, a błędy nie zawierają treści odpowiedzi. Powierzony adapter `fetch` widzi nagłówki uwierzytelnienia i musi być zaufany oraz nie może ich logować. Kompozycję z preflightem sprawdzono testami z fikcyjnymi poświadczeniami i odpowiedziami HTTP.

[Drugi przebieg sondy Actions](https://github.com/OtisRed/agent-github-flow/actions/runs/41445095041/attempts/2) uruchomił dokładnie przypiętą, przejrzaną wersję tej kompozycji na rzeczywistym issue z osobną kartą w izolowanym Projectcie. Oddzielny PAT i token App przeszły pełne odczyty, a koordynator zatrzymał się na oczekiwanym `unverified-snapshot` bez wykonania kroków zapisu. Osobny odczyt po zakończeniu potwierdził niezmieniony status testowej karty. Sonda nie sprawdza mutacji, produkcyjnej polityki zaufania, wyłączności właściciela ani pełnego kontrolera. Pierwszy przebieg zakończył się błędem; jego diagnostyka wskazała brak PAT w testowym środowisku.

W osobnym prywatnym repozytorium i prywatnym Project z syntetycznymi issue uruchomiono przez uwierzytelnione CLI sześć kroków inicjalizacji: checkpoint Projectu, znacznik issue, status, potwierdzenie Projectu, potwierdzenie issue i normalizację checkpointu. Po każdym kroku ponownie odczytano dane; status osiągnął `agent-ready`, a treść issue zachowano. Na drugim syntetycznym issue celowo zakończono proces po zmianie statusu i uruchomiono osobny proces: odczytał stan pośredni i dokończył sekwencję. Odczyt końcowy potwierdził status obu kart. Cele próby były przypięte do konkretnych identyfikatorów testowych i poddane niezależnemu przeglądowi subagenta.

Następnie na pierwszym syntetycznym issue dodano drugi poprawny komentarz i przeprowadzono pięć kroków kolejnego handoffu: checkpoint `pending`, znacznik `pending`, status `review`, potwierdzenie Projectu i issue. Ostatni pełny odczyt zwrócił `unchanged`; przed i po każdej mutacji sprawdzano również wcześniejszy komentarz, także po usunięciu go z checkpointu Projectu. Użyto tego samego odizolowanego konta użytkownika i testowej karty.

Po złożeniu czytników wykonano kolejną pełną próbę handoffu i osobno inicjalizacji po reopen przy użyciu wspólnego `createFlowSnapshotReader`, w tym osobnego readbacku dawnego komentarza po normalizacji. Następnie ograniczony koordynator `runFlowCycle` sam wykonał pięć kroków kolejnego syntetycznego handoffu i zakończył z `unchanged`. Dla dokładnie przypiętej prywatnej fixture warunki zaufania i jednego writera ustalono jawnie w kodzie próby; sam czytnik ich nie ustala. Wszystkie te sekwencje i końcowe odczyty zakończyły się powodzeniem.

Następnie pierwsze syntetyczne issue zamknięto i ponownie otwarto. `src/flow-native-epoch-reader.mjs` odczytał i sprawdził pełną historię natywną bez wymagania komentarza; `src/flow-reentry-runner.mjs` i adapter zapisu w czterech krokach zapisali sentinel, ustawili `needs-design`, usunęli dokładnie stary znacznik i potwierdzili sentinel. Kolejny przebieg zwrócił `already-reentered`. Stary komentarz odmówiono jako należący do wcześniejszej epoki; nowe przekazanie przeszło sześć kroków bootstrapu i osiągnęło `agent-ready`. Po nim kolejny przebieg reentry również zwrócił `already-reentered`. Przy każdym zapisie i readbacku weryfikowano historię oraz wcześniejszy komentarz.

Pierwsza próba reopen na drugim syntetycznym issue zatrzymała się po zapisie sentinela: niezależny odczyt wykazał ponowne zamknięcie issue. Historia pokazuje odrębne zdarzenie zamknięcia po ręcznym reopen. W testowym Projectcie włączony był wbudowany workflow `Auto-close issue` dla standardowego statusu `Done`, a status tej karty po zamknięciu był `Done`; to możliwy konflikt, lecz sama sekwencja nie dowodzi, który mechanizm wykonał zamknięcie. Regułę wyłączono w testowej tablicy przed udaną próbą na pierwszym issue. Następnie drugie issue ponownie otwarto: po odczycie starego `pending`, nowego eventu i pierwotnego komentarza proces zapisał nowy sentinel, ustawił `needs-design`, usunął stary znacznik i potwierdził wynik. Kolejny przebieg zwrócił `already-reentered`. [Dokumentacja GitHuba](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-built-in-automations) opisuje możliwość automatycznego zamykania issue po zmianie statusu.

Tę samą regułę `Auto-close issue` znaleziono aktywną w Projectcie globalnego flow dla statusu `done` i wyłączono, zgodnie z zasadą, że zamknięcie issue jest decyzją właściciela. Setup każdego kolejnego projektu musi sprawdzić konkurujące automaty Projectu, w szczególności automatyczne zamykanie, i nie uruchamiać dwóch właścicieli tej samej zmiany. Pozostałych reguł Projectu nie zmieniano.

Opisane powyżej próby zapisu nie używały produkcyjnej karty ani nie były uruchomieniem docelowych Actions. Nie dowodzą obsługi równoczesnych edycji, odpowiedzi timeout po faktycznym zapisie ani automatyzacji nocnej. Zaufanie i wyłączność zapisu były założeniami odizolowanej fixture, nie dowodem konfiguracji produkcyjnej. Prywatne środowisko testowe pozostaje oznaczone jako syntetyczne do dalszej weryfikacji.

## Odzyskiwanie w badanym wariancie dwóch zapisów

Kolejność zapisu jest podana wyżej: `pending` w Project przed `pending` w issue, następnie status i osobne potwierdzenia w Project oraz issue. Wcześniejszy pomysł zapisu wyłącznie do issue nie stanowi instrukcji dla tego wariantu.

Przerwanie po `pending`, ale przed zmianą karty: jeśli obie wartości i status odpowiadają jednemu z opisanych etapów, model dopuszcza odpowiedni kolejny krok po świeżej weryfikacji. Przerwanie po zmianie karty, ale przed `committed`: jeśli karta ma cel i pozostałe dowody się zgadzają, model dopuszcza potwierdzenia w przewidzianej kolejności. Inny status lub inne przekazanie blokuje automatyczne zgadywanie. Dla zgodnej pary `committed` i zweryfikowanego komentarza zgodna karta nie wymaga działania; jednoznaczny mismatch można zaplanować do naprawy po świeżym odczycie. `done`, zamknięcie i ponowne otwarcie issue należą do odrębnej synchronizacji natywnego stanu.

Potwierdzenie `committed` oznacza jedynie, że odczytano oczekiwany status, nie że udowodniono, kto go zapisał. Może to być również wynik równoczesnej zmiany ręcznej. Przed uruchomieniem integracja musi ustalić jednego właściciela zapisu i wspólną serializację ścieżek #5/#6 oraz obsłużyć niejednoznaczne równoczesne zmiany; sama serializacja Actions w jednym repozytorium nie obejmuje innych repozytoriów ani ręcznych edycji.

### Docelowy kierunek: centralny wykonawca Projectów

Decyzja właściciela: centralny kontroler w `agent-github-flow` ma być jedynym automatycznym właścicielem zapisów do każdej podłączonej tablicy, zarówno po zdarzeniu jak i w nocnej kontroli. Repozytorium projektu nie uruchamia drugiego kontrolera zapisującego. Uzgodniony kierunek wymaga jeszcze implementacji, dowodu zaufania, konfiguracji i migracji istniejących właścicieli.

Wariant wyzwalania do sprawdzenia: niewielki relay w repozytorium źródłowym reaguje na utworzenie, edycję i usunięcie komentarza oraz potrzebne zmiany native issue, wysyła do centrum sygnał z minimalnymi identyfikatorami, a centralny kontroler ponownie pobiera dane z GitHuba i sprawdza zgodność repozytorium, issue i Projectu z zaufaną konfiguracją. Sygnał jest wyłącznie powiadomieniem, nie dowodem uprawnienia, treści ani kolejności; musi być odporny na powtórzenie i nie może zawierać prywatnej treści. Natywne zdarzenia same nie uruchamiają workflow w innym repozytorium.

[Repository dispatch](https://docs.github.com/en/rest/repos/repos#create-a-repository-dispatch-event) jest kandydatem na transport. Wymaga poświadczenia z `contents:write` do centralnego repozytorium; standardowy `GITHUB_TOKEN` repozytorium źródłowego nie daje takiego dostępu do innego repozytorium. Tego uprawnienia nie należy nazywać „tylko wysyłką sygnału”: pozwala ono także na inne operacje na zawartości w zakresie tokenu. Rozprowadzenie klucza centralnej aplikacji albo PAT osobistych Projectów do projektów nie jest częścią tego wariantu. Źródło, zakres i rotacja osobnego poświadczenia relay, ochrona repozytorium centralnego oraz alternatywy wymagają osobnej weryfikacji. Przypadek własnego repozytorium kontrolera może korzystać ze zdarzenia lokalnego i trzeba go sprawdzić osobno; nie może uruchomić konkurencyjnej ścieżki zapisu.

Centralny rejestr powinien wiązać repozytorium i issue z właściwym Projectem i opcjami statusu oraz ograniczać jawnie dozwolone źródła i tożsamości. Dla publicznego repozytorium kod, nazwy przebiegów i logi mogą być publiczne: nie umieszczać w nich nazw prywatnych repozytoriów, treści issue, identyfikatorów prywatnych kart ani tokenów. Szczegółowe dane konfiguracyjne i diagnostyczne muszą mieć właściwą ochronę; nie zakładać, że maskowanie sekretów anonimizuje logi.

### Odczytowy odbiornik zdarzeń

`flow-event-preflight` rozpoznaje zdarzenia issue własnego repozytorium oraz `repository_dispatch` z innych repozytoriów. Nie pobiera danych issue, nie podejmuje decyzji o statusie i niczego nie zapisuje. Publiczny payload sygnału zawiera wyłącznie losowy 32-znakowy identyfikator źródła i numer issue, a mapowanie źródła na repozytorium jest konfiguracją chronionego środowiska `flow-controller` (`FLOW_EVENT_ROUTES`). Identyfikator służy do routingu, nie jest dowodem tożsamości ani uprawnieniem; przed każdym zapisem przyszły kontroler musi osobno sprawdzić dane, zaufanie i właściciela. Konfiguracja i wyniki nie są wypisywane do logu. Nie należy utożsamiać braku nazwy prywatnego repozytorium w payloadzie z gwarancją ukrycia wszystkich metadanych; numer issue nadal jest przekazywany.

Przed zapisaniem konfiguracji trzeba skonfigurować i zweryfikować ochronę środowiska oraz dostęp do niego. Workflow zadziała dopiero po umieszczeniu go na domyślnej gałęzi. Relay, poświadczenie do niego, faktyczne wyzwolenie z VSone, serializacja i produkcyjny kontroler nadal nie są gotowe ani potwierdzone. Testy jednostkowe i lokalne sprawdzają wyłącznie rozpoznawanie oraz logowanie, nie prywatność całej platformy ani uprawnienia nadawcy.

### Przygotowany relay projektu

Przygotowano współdzielony workflow `flow-relay.yml` i niewielki nadawca. W docelowym wariancie workflow projektu wywoła go po zdarzeniu dotyczącym issue; kod jest pobierany z dokładnego commitu współdzielonego workflow, a wywołanie powinno być przypięte do przejrzanego SHA. Nadawca wysyła do API GitHuba tylko alias i numer issue, nie treść komentarza ani nazwę prywatnego repozytorium; token, alias i docelowe repozytorium ma pobierać ze środowiska `flow-relay` repozytorium wywołującego. Workflow wywołujący musi jawnie przekazać nazwy sekretów `FLOW_RELAY_TOKEN` i `FLOW_RELAY_SOURCE`; sama deklaracja środowiska w workflow współdzielonym nie wystarczy. Wartość docelową dostarcza zmienna środowiska `FLOW_RELAY_TARGET`. Należy przedtem jawnie utworzyć i zabezpieczyć to środowisko oraz ograniczyć osobny token do centralnego repozytorium. `contents:write` jest szersze niż samo dispatch i nie jest równoważne ograniczeniu uprawnień do tego endpointu. Nie przekazywać PAT Projectu ani prywatnego klucza App do repozytorium projektu.

Przykład wywołania po dopuszczeniu konkretnej wersji; `<SHA>` trzeba zastąpić pełnym, zweryfikowanym commitem, a środowisko i wartości skonfigurować wcześniej w repozytorium projektu:

```yaml
name: Flow wakeup
on:
  issue_comment:
    types: [created, edited, deleted]
  issues:
    types: [opened, closed, reopened]
permissions:
  contents: read
jobs:
  relay:
    uses: OtisRed/agent-github-flow/.github/workflows/flow-relay.yml@<SHA>
    secrets:
      FLOW_RELAY_SOURCE: ${{ secrets.FLOW_RELAY_SOURCE }}
      FLOW_RELAY_TOKEN: ${{ secrets.FLOW_RELAY_TOKEN }}
```

Przykład wymaga uruchomienia w celu sprawdzenia przepływu sekretów środowiska i skuteczności ochrony. Nie należy zastępować jawnego mapowania przez `secrets: inherit`.

Walidator actionlint 1.7.12 nie rozpoznaje jeszcze udokumentowanych pól `job.workflow_repository` i `job.workflow_sha` ([issue narzędzia](https://github.com/rhysd/actionlint/issues/757)). Konfiguracja wycisza wyłącznie te dwie diagnozy, tylko dla workflow relay; pozostałe kontrole oraz ujemna próba walidatora pozostają w CI. Wynik CI nie potwierdza rzeczywistej dostępności pól podczas wywołania reusable workflow.

Testy modułu używają atrap transportu, nie wykonują zapytań. Wynik 204 znaczy jedynie, że GitHub przyjął sygnał; nie potwierdza wykonania odbiornika, dostarczenia ani zmiany stanu. Błąd lub timeout daje niejednoznaczny wynik bez automatycznego ponowienia. Ponieważ `repository_dispatch` wymaga workflow na gałęzi domyślnej odbiorcy, pełna kontrolowana próba wymaga najpierw przygotowania i przyjęcia odbiornika zgodnie ze zwykłym procesem, oraz osobnej konfiguracji repozytorium źródłowego. Sam współdzielony workflow nie jest włączonym relayem VSone.

### Współbieżność, odzyskiwanie i wymagane próby

Zdarzeniowy kontroler i nocny reconcile muszą współdzielić jedną zweryfikowaną serializację zapisu dla tej samej tablicy lub karty. Osobne tablice mogą działać równolegle. Wybór ziarna blokady i sposób przekazania tożsamości karty do grupy joba należy sprawdzić przed implementacją; ten sam issue może występować w wielu tablicach i zapis jego body może wymagać szerszej serializacji. Nie zakładać trwałości lub nieograniczonej pojemności kolejki Actions: [domyślnie oczekujące przebiegi mogą zostać zastąpione](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency); również skonfigurowana kolejka jest ograniczona. Nocna kontrola pomaga wykryć rozbieżności, ale harmonogram może się opóźnić albo nie wykonać.

Przed zapisem potrzebne są dowody poprawnego źródła, zaufania, kompletności odczytu i jedynego automatycznego właściciela, ponowny odczyt i readback. Serializacja Actions nie blokuje ręcznej edycji, innych tokenów ani nieznanych aplikacji; nie daje transakcji ani compare-and-swap Projectu. Niepewny lub częściowy zapis blokuje ślepe ponowienie.

Próby przed wdrożeniem: repozytorium źródłowe inne niż centrum i własne repozytorium centrum; poprawny, fałszywy, powtórzony i spóźniony sygnał; brak relay, niepoprawne poświadczenie i nieautoryzowane źródło; równoczesny komentarz i reconcile; różne tablice równolegle; edycja i usunięcie komentarza, close/reopen, przerwanie i pominięty przebieg; brak ujawnienia prywatnych danych w publicznych logach; brak pętli zdarzeń wywołanych przez kontroler. Osobno sprawdzić rzeczywisty odczyt i kontrolowany zapis z chronionego centralnego środowiska. Żadna z tych prób nie jest potwierdzona samym projektem.

## Granice modelu

`src/flow-recovery.mjs` wyłącznie oblicza kolejny krok na dostarczonym snapshotcie; nie przeprowadza uwierzytelniania, stronicowania, zapisu, odczytu po zapisie ani blokowania współbieżności. Flagi `complete`, `trusted`, `markerProvenanceVerified`, `currentEpochVerified` i `singleWriterVerified` są zapewnieniami przyszłego wywołującego, nie dowodem uzyskanym przez funkcję. Dopóki wywołujący nie ma podstaw do ich potwierdzenia, musi odmówić działania.
