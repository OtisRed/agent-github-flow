# Prototyp koordynacji wdrożeń — AGF #189

To prototyp integracji AGF, nie działające automatyczne wdrożenie Chefa. Nie instaluje projektowego wykonawcy ani nie konfiguruje webhooka. Worker wykrywa zmiany przez odczyt GitHuba w cyklu 60 sekund i po restarcie; jest domyślnie wyłączony. Nie inicjalizować jego magazynu na produkcji przed ukończeniem integracji i testów.

- `deployment_state.py` przechowuje zidentyfikowane próby i serializuje je dla repozytorium. Nierozstrzygnięta lub nieudana próba blokuje kolejną. Powtórzenie tego samego ID nie uruchamia ponownie wcześniejszej operacji.
- `deployment_worker.py` przyjmuje zaufane funkcje sprawdzenia wersji oraz wykonania. Przed wywołaniem ponawia weryfikację; po niepotwierdzonej odpowiedzi zapisuje stan nieznany. Ponowne uzgodnienie wymaga wiarygodnego wyniku tej samej próby z projektu. Moduł sam nie uwierzytelnia źródła wyniku.
- `deployment_executor.py` uruchamia wyłącznie stałą komendę dostarczoną przez zaufaną konfigurację, przekazuje JSON i nie używa powłoki. Nie tworzy granicy uprawnień ani nie udowadnia, że projekt zakończył wdrożenie; niezaufana konfiguracja polecenia byłaby niedopuszczalna.
- `deployment_source.py`, `deployment_dispatch.py` i `deployment_schedule.py` sprawdzają aktualny pełny SHA i najnowsze wymagane checki z określonych GitHub Apps, ponawiają sprawdzenie przed zleceniem i zapisują niepewność zamiast ponawiać nieznany wynik. Sukces wymaga potwierdzonego przez wykonawcę działającego SHA. Przed promocją zapisywany jest trwały dowód zaakceptowanego prefiksu (identyfikatory `issue-N` oraz commity); dla `main` worker sprawdza rodziców commita i scalony PR przed przekazaniem zakresu projektowi. Zmiany poza prefiksem nie są przekazywane. Bez dowodu promocji `main` pozostaje zablokowany.
- Kontrakt procesu: wejście JSON `{"action":"deploy"|"status","request":{id,repository_id,target,commit,changes}}`; wynik zawiera dokładnie `id`, `target`, `commit`, `observed_commit`, `status`. `succeeded` w odpowiedzi `status` musi potwierdzać zakończenie całej próby, włącznie z kontrolą i wymaganym sprzątaniem, a nie tylko uruchomienie kontenera. Zaufany projektowy wykonawca odpowiada za rzeczywisty pomiar wersji i ponowne sprawdzenie aktualności gałęzi przed przełączeniem. AGF nie uruchamia poleceń pochodzących z żądania ani webhooka.
- Opcjonalna konfiguracja `deployment_guarded` i `deployment_state_path` sprawia, że istniejący worker promocji wymaga potwierdzonego, zgodnego z bieżącym `main` wdrożenia produkcyjnego. Trzyma blokadę SQLite przez krok promocji, aby inne próby korzystające z tego samego magazynu nie rozpoczęły się w tym czasie. Pozostałe projekty zachowują dotychczasowe działanie. Brak lub nieprawidłowy magazyn kończy się błędem, a nie automatycznym utworzeniem.

Do ukończenia pozostają: projektowy wykonawca i ograniczenie jego uprawnień, sprawdzenie zgodności mapowania `issue-N` z manifestem Jedzenia, niezależne potwierdzenie rzeczywistej wersji i stanu sprzątania przez wykonawcę, obsługa zatwierdzonych zmian `main` bez potwierdzenia promocji AGF, raportowanie błędów do issue oraz kontrolowany bootstrap istniejącego `main`. Obecny ręcznie uruchomiony Chef-test nie jest podłączony do workera. Nie ma atomowej transakcji obejmującej GitHub i host. Testy prototypu używają wyłącznie fikcyjnych danych.
