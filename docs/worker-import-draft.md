# Roboczy import sygnałów dla workera

Niekompletny zakres issue #81: stronicowany odczyt identyfikatorów z kolejki przyjęć i idempotentny import do osobnego prywatnego magazynu. Import używa istniejącego ID dostawy i nie usuwa źródła. Marker strony jest wyłącznie chwilowy: po wyczerpaniu budżetu stron lub czasu przyszły scheduler musi kontynuować bieżący przebieg, zamiast stale wracać do pierwszych stron. Po dojściu do końca rozpoczyna kolejny pełny przebieg, aby odnaleźć nowe ID przed markerem; także po pustym wyniku musi kiedyś wznowić skan. Po restarcie może zacząć od początku, ale trzeba zaprojektować i przetestować zapewnienie postępu i sprawiedliwości także przy ciągłym napływie zdarzeń. Automatycznego schedulera jeszcze tu nie ma.

Odłączony model `ScanScheduler` wykonuje po jednej stronie na wywołanie, trzyma marker w pamięci, zachowuje go po zablokowanym odczycie lub błędzie magazynu i zeruje po końcu przebiegu. Odrzuca równoczesny krok tej samej instancji. Test połączył go z rzeczywistymi modelami dwóch magazynów na syntetycznych zdarzeniach, także dla ID dodanego przed markerem. To nie jest cykliczny proces: wywołujący musi zapewnić dalsze kroki, jedną instancję na źródło, tę samą zaufaną konfigurację i blokadę. Ciągły napływ nie ma jeszcze udowodnionej sprawiedliwości ani ograniczenia czasu pełnego przebiegu; po awarii skan wraca na początek.

Magazyn importu jest odrębny od bazy #77 i od checkpointu FLOW. Import strony kończy się sukcesem tylko po zatwierdzeniu transakcji; ponowienie jest idempotentne. Utrzymanie jednej zaufanej ścieżki kolejki i jednej ścieżki magazynu jest obowiązkiem przyszłej konfiguracji. Zmienienie źródła lub cofnięcie bazy wymaga osobnej obsługi; to nie jest automatycznie wykrywane.

Eksperymentalny format magazynu ma wersję 11; starszych formatów z wcześniejszych commitów draftu nie migruje. Odrzucenie nieznanej bazy wymaga jawnego odzyskania danych, nie automatycznego wymazania pliku. Format v9 nie zapisywał kolejności importu, więc ewentualna migracja istniejących danych nie potrafi jej odtworzyć i wymaga jawnej polityki.

Blokada `flock` używa wspólnej ścieżki niezależnej od ścieżki magazynu: procesy podające tę samą ścieżkę blokady wykluczają się także przy różnych magazynach. To nie wymusza jednak, by wszystkie procesy wskazywały tę samą ścieżkę. Sprawdzenie tożsamości pliku wykrywa widoczną w danym momencie podmianę, ale nie jest atomowym fencingiem. Przed prawdziwymi operacjami GitHub konieczne są zaufana konfiguracja, pojedyncza stała ścieżka, zaufany katalog, zakaz podmiany pliku i projekt jednej globalnej wyłączności.

Nowa baza jest tworzona wyłącznie w jawnym trybie bootstrapu `allow_create=True`: jako prywatny plik tymczasowy, a dopiero po inicjalizacji i synchronizacji publikowana bez nadpisania istniejącej ścieżki. Zwykłe uruchomienie domyślnie odmawia pracy, gdy baza znikła, by nie utracić informacji o niepewnych zapisach. Nie wolno pozostawić automatycznego bootstrapu w normalnej konfiguracji workera; zaufana rejestracja pierwszego uruchomienia i odzyskiwanie utraconej bazy nadal wymagają projektu. Przerwanie przed publikacją nie powinno zostawiać pustej bazy docelowej; może pozostawić plik tymczasowy wymagający osobnej polityki sprzątania. Nieznana istniejąca baza i osierocony dziennik przy braku bazy są odrzucane bez automatycznego usuwania. Testy przerwania procesu obejmują wybrane momenty przed i po publikacji, ale nie dowodzą zachowania systemu plików przy zaniku zasilania.

Model zapisuje `pending` i pozwala trwale zarezerwować jeden wpis jako `running`; unikalny indeks uniemożliwia przechowywanie dwóch aktywnych lub niepewnych wpisów w tej samej bazie. Przed przyszłą mutacją może ustawić odrębne znaczniki `ref_intent` i `status_intent`; oba mogą pozostać aktywne jednocześnie, aby nie zgubić niepewnego zapisu statusu podczas publikacji rezerwacji w gałęzi. Przy ponownym przejęciu blokady pozostawiony `running` lub `recovering` staje się `uncertain`, a oba znaczniki zostają zachowane. Jeśli niepewność dotyczy wyłącznie statusu, model umożliwia zarezerwowanie jego sprawdzenia jako `recovering`; może zachować zamiar kolejnego zapisu refu bez utraty znacznika statusu, ale samo zapisanie intencji nie jest zgodą na wysłanie: model nie wykonuje odczytów, oczekiwania ani ponowienia. Niepewnego refu nie dopuszcza do tej ścieżki. Żadna z tych operacji nie wykonuje mutacji; odróżnienie zależy od tego, czy przyszły wykonawca niezawodnie zapisze właściwą intencję przed każdym wysłaniem. Niepewne i rozpoczęte wpisy blokują kolejne rezerwacje; nie są automatycznie ponawiane ani nazywane wykonanymi. Nie ma jeszcze zweryfikowanego podłączenia rozliczenia intencji, produkcyjnego wywołania kontrolera, zapisu GitHuba, ponowienia po 120 sekundach, monitoringu ani archiwizacji. Nie włączono produkcyjnego webhooka i nie stosuje się tego magazynu do rzeczywistej pracy. Testy używają wyłącznie tymczasowych baz i syntetycznych danych; ponowne otwarcie oraz zakończenie procesu nie są testem restartu serwera ani awarii sprzętu.

Ledger potrafi oznaczyć jako `completed` wpis `running` bez jakiejkolwiek intencji zapisu, gdy zaufany wywołujący uprzednio stwierdził brak potrzebnej operacji. Ta prywatna metoda jedynie zapisuje wniosek; nie weryfikuje go i nie jest podłączona do workera. ID zostaje w bazie, by ponowny import nie wznowił tej samej dostawy. Docelowa retencja musi zapewnić deduplikację względem zachowanych danych wejściowych; migracja istniejącej bazy i polityka odtwarzania wymagają osobnego opracowania.

Nowym dostawom ledger nadaje rosnący numer w transakcji importu; duplikat zachowuje swój poprzedni numer i stan. Wybór oczekującej pracy używa tej kolejności pierwszego importu, nie sortowania po UUID. Nie dowodzi to kolejności zdarzeń GitHuba ani postępu przed importem: niepewny wpis może blokować całą kolejkę, a skan nadal wymaga polityki fairness. Wyczerpanie licznika zatrzymuje import nowych wpisów; duplikaty nadal są rozpoznawane.

Osobna sonda `worker-recovery-observe.mjs` wiąże syntetyczny stan `recovering` z ID dostawy, rzeczywistym resolverem i `runFirstV3Cycle` z przypiętego draftu #25, przy czym zastępuje obie fabryki zapisu blokadami. Dla starego statusu test sprawdza 120 sekund na **wirtualnym zegarze** i obserwacje przed próbą rezerwacji; dla widocznego statusu docelowego sprawdza osobną ścieżkę bez oczekiwania. Zmiana danych podczas oczekiwania blokuje próbę. Wynik sondy nie jest potwierdzeniem uprawnień, wyniku GitHuba ani zgodą na mutację. Przed wywołaniem cyklu sonda porównuje ID dostawy, wynik resolvera, rejestrację i kontekst cyklu; test blokuje przypadek innego issue. Wszystkie wstrzyknięte zależności pozostają zaufanymi callbackami, nie są sandboxowane. Przyszły runtime musi przypiąć kod, zapewnić zaufane rzeczywiste odczyty i monotoniczny zegar, ochronę gałęzi oraz zapis intencji przed transportem.

Przed przyszłym zapisem statusu ledger wymaga teraz przechowania HMAC i identyfikatora historycznego klucza w tej samej transakcji co intencja. Pomocniczy signer używa osobnej domeny HMAC i materiału istniejącego klucza checkpointu; obejmuje ID dostawy, pełny binding v3 oraz ID karty i obu opcji, nie zwracając tych danych w wyniku. Sam ledger porównuje podany MAC z zapisem: nie potrafi dowieść, że wyliczono go ponownie ze świeżego, uwierzytelnionego stanu. Taki odczyt, weryfikacja MAC komentarza i rejestracji, zaufanie do adaptera i dostęp do historycznego klucza pozostają wymaganiami integracji. Obecny keyring #25 nie udostępnia jeszcze tej nowej domeny. Sama zgodność MAC nie chroni przed równoczesnym cofnięciem ledgeru i gałęzi; po odtworzeniu stanu bez niezależnej kotwicy potrzebne jest zatrzymanie i uzgodnienie.

Po potwierdzonej nowej rezerwacji `checkpointOid` i czas rezerwacji celowo się zmieniają. Signer potrafi z poprzedniego bindingu skonstruować commitment przejścia dopuszczający tylko nowy HEAD i czas rezerwacji; ledger zapisuje planowany old/new/tree oraz commitment w tej samej transakcji co ref_intent, zachowując status_intent. Ledger weryfikuje kształt i zgodność starego MAC, ale nie weryfikuje sam HMAC przejścia ani wyniku GitHuba. Ledger posiada prywatną operację atomowego zastąpienia commitmentu i rozliczenia refu przy identycznym zapisanym planie, ale sama ta operacja nie potwierdza observed ani HMAC. Nie ma jeszcze podłączonego zaufanego adaptera produkcyjnego, który sprawdzi wynik GitHuba i wywoła ją dopiero po pełnej weryfikacji. Przerwanie przed zatwierdzeniem aktualizacji ledgeru ma zachować obie niepewności; po zatwierdzeniu pozostaje niepewność statusu, pod warunkiem że przyszły adapter rzeczywiście zweryfikował ref przed aktualizacją. Nie ponawiać niepewnego refu w ciemno.

Odłączony `worker-reservation-guard.mjs` sprawdza związanie rezerwacji ze stanem issue i tablicy oraz odczytuje zapisany plan przed wywołaniem publikacji i przed potwierdzeniem. Syntetyczny test łączy faktyczny cykl v3 i ledger SQLite przez kanał dostępny tylko w testach; podstawia fikcyjne odczyty i zapisy GitHuba oraz wirtualny zegar. Opcjonalna kontynuacja używa faktycznego kroku statusu z syntetycznym transportem, po sprawdzeniu zachowanej intencji i nowego MAC; nawet po obserwacji statusu `status_intent` pozostaje aktywny, a końcowy commit jest zablokowany. Sam guard przyjmuje zaufane callbacki i nie wymusza syntetycznego transportu: brak rzeczywistych zapisów wynika z konfiguracji testu i braku produkcyjnego runtime'u. To nie jest działający worker ani produkcyjny adapter IPC: nadal trzeba podłączyć zaufane źródła, keyring, rzeczywiste operacje i obsługę niepewności oraz sprawdzić cały cykl przed wdrożeniem.

Autor jest porównywany pomiędzy odczytami pojedynczej próby, ale jego ID nie jest częścią trwałego commitmentu v3; po restarcie model polega więc na niezmienności autora komentarza GitHuba o danym ID. Porównanie stanu GitHuba i zapisu w SQLite nie jest atomowe: nawet po końcowym odczycie może nastąpić równoczesna zmiana przed potwierdzeniem w ledgerze. Wdrożenie wymaga jednej chronionej ścieżki zapisu refu oraz jawnego rozstrzygnięcia tej granicy; syntetyczne testy jej nie eliminują.

Osobny signer i mechaniczne metody ledgeru modelują plan końcowego commitu: keyed MAC wiąże pełną podaną treść rekordu z wcześniejszą intencją i old/new/tree, a ledger zachowuje obie intencje do atomowego rozliczenia. Te metody nie weryfikują poprawności ani ciągłości rekordu, zawartości tree, podpisu planu, odpowiedzi GitHuba czy uprawnień; nie zostały połączone z guardem ani prawdziwym workerem. Wyłącznie zaufany adapter, po pełnej weryfikacji, może wywołać ich prywatny prymityw zakończenia. Testy awarii procesu sprawdzają mechanikę transakcji, nie dowodzą publikacji checkpointu.

Odłączone `matchesFinalContext` porównuje cały kontekst przed i po oczekiwanej zmianie rekordu pending→committed, kontroluje ciągłość v3 i receipt oraz sprawdza otwarte issue, wskazaną kartę i docelową opcję. Oczekiwane identyfikatory karty i opcji musi dostarczyć caller z uwierzytelnionego commitmentu. Porównanie nie uwierzytelnia odczytów, nie weryfikuje całego drzewa, refów ani ochrony i samo nie uprawnia do rozliczenia dostawy.

Ograniczony format commitmentu przyjmuje kanoniczne daty UTC od roku 0001; jest to celowo węższe niż obecny parser v3, który technicznie dopuszcza rok 0000. Odrzucona data zatrzymuje próbę, nie jest normalizowana.
