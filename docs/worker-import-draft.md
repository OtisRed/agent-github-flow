# Roboczy import sygnałów dla workera

Niekompletny zakres issue #81: stronicowany odczyt identyfikatorów z kolejki przyjęć i idempotentny import do osobnego prywatnego magazynu. Import używa istniejącego ID dostawy i nie usuwa źródła. Marker strony jest wyłącznie chwilowy: po dojściu do końca lub po wyczerpaniu przyszłego budżetu stron/czasu trzeba rozpocząć nowy przebieg od początku. Nowy identyfikator przed markerem zostanie odnaleziony w kolejnym pełnym przebiegu. Skan musi być ponawiany także po pustym wyniku; tego harmonogramu jeszcze tu nie ma.

Magazyn importu jest odrębny od bazy #77 i od checkpointu FLOW. Import strony kończy się sukcesem tylko po zatwierdzeniu transakcji; ponowienie jest idempotentne. Utrzymanie jednej zaufanej ścieżki kolejki i jednej ścieżki magazynu jest obowiązkiem przyszłej konfiguracji. Zmienienie źródła lub cofnięcie bazy wymaga osobnej obsługi; to nie jest automatycznie wykrywane.

Eksperymentalny format magazynu ma wersję 4; starszych formatów z wcześniejszych commitów draftu nie migruje. Odrzucenie nieznanej bazy wymaga jawnego odzyskania danych, nie automatycznego wymazania pliku.

Blokada `flock` używa wspólnej ścieżki niezależnej od ścieżki magazynu: procesy podające tę samą ścieżkę blokady wykluczają się także przy różnych magazynach. To nie wymusza jednak, by wszystkie procesy wskazywały tę samą ścieżkę. Sprawdzenie tożsamości pliku wykrywa widoczną w danym momencie podmianę, ale nie jest atomowym fencingiem. Przed prawdziwymi operacjami GitHub konieczne są zaufana konfiguracja, pojedyncza stała ścieżka, zaufany katalog, zakaz podmiany pliku i projekt jednej globalnej wyłączności.

Nowa baza jest tworzona wyłącznie w jawnym trybie bootstrapu `allow_create=True`: jako prywatny plik tymczasowy, a dopiero po inicjalizacji i synchronizacji publikowana bez nadpisania istniejącej ścieżki. Zwykłe uruchomienie domyślnie odmawia pracy, gdy baza znikła, by nie utracić informacji o niepewnych zapisach. Nie wolno pozostawić automatycznego bootstrapu w normalnej konfiguracji workera; zaufana rejestracja pierwszego uruchomienia i odzyskiwanie utraconej bazy nadal wymagają projektu. Przerwanie przed publikacją nie powinno zostawiać pustej bazy docelowej; może pozostawić plik tymczasowy wymagający osobnej polityki sprzątania. Nieznana istniejąca baza i osierocony dziennik przy braku bazy są odrzucane bez automatycznego usuwania. Testy przerwania procesu obejmują wybrane momenty przed i po publikacji, ale nie dowodzą zachowania systemu plików przy zaniku zasilania.

Model zapisuje `pending` i pozwala trwale zarezerwować jeden wpis jako `running`. Przed przyszłą mutacją może ustawić odrębne znaczniki `ref_intent` i `status_intent`; oba mogą pozostać aktywne jednocześnie, aby nie zgubić niepewnego zapisu statusu podczas publikacji rezerwacji w gałęzi. Przy ponownym przejęciu blokady pozostawiony `running` staje się `uncertain`, a oba znaczniki zostają zachowane. Żadna z tych operacji nie wykonuje mutacji; odróżnienie zależy od tego, czy przyszły wykonawca niezawodnie zapisze właściwą intencję przed każdym wysłaniem. Niepewne i rozpoczęte wpisy blokują kolejne rezerwacje; nie są automatycznie ponawiane ani nazywane wykonanymi. Nie ma jeszcze sposobu wejścia w odzyskiwanie niepewnego wpisu, potwierdzania zakończonej intencji, stanu `completed`, wywołania kontrolera, zapisu GitHuba, ponowienia po 120 sekundach, monitoringu ani archiwizacji. Nie włączono produkcyjnego webhooka i nie stosuje się tego magazynu do rzeczywistej pracy. Testy używają wyłącznie tymczasowych baz i syntetycznych danych; ponowne otwarcie oraz zakończenie procesu nie są testem restartu serwera ani awarii sprzętu.
