# Roboczy import sygnałów dla workera

Niekompletny zakres issue #81: stronicowany odczyt identyfikatorów z kolejki przyjęć i idempotentny import do osobnego prywatnego magazynu. Import używa istniejącego ID dostawy i nie usuwa źródła. Marker strony jest wyłącznie chwilowy: po dojściu do końca lub po wyczerpaniu przyszłego budżetu stron/czasu trzeba rozpocząć nowy przebieg od początku. Nowy identyfikator przed markerem zostanie odnaleziony w kolejnym pełnym przebiegu. Skan musi być ponawiany także po pustym wyniku; tego harmonogramu jeszcze tu nie ma.

Magazyn importu jest odrębny od bazy #77 i od checkpointu FLOW. Import strony kończy się sukcesem tylko po zatwierdzeniu transakcji; ponowienie jest idempotentne. Utrzymanie jednej zaufanej ścieżki kolejki i jednej ścieżki magazynu jest obowiązkiem przyszłej konfiguracji. Zmienienie źródła lub cofnięcie bazy wymaga osobnej obsługi; to nie jest automatycznie wykrywane.

Eksperymentalny format magazynu ma wersję 2; starszego formatu z wcześniejszego commita draftu nie migruje. Odrzucenie nieznanej bazy wymaga jawnego odzyskania danych, nie automatycznego wymazania pliku.

Blokada `flock` używa wspólnej ścieżki niezależnej od ścieżki magazynu: procesy podające tę samą ścieżkę blokady wykluczają się także przy różnych magazynach. To nie wymusza jednak, by wszystkie procesy wskazywały tę samą ścieżkę. Sprawdzenie tożsamości pliku wykrywa widoczną w danym momencie podmianę, ale nie jest atomowym fencingiem. Przed prawdziwymi operacjami GitHub konieczne są zaufana konfiguracja, pojedyncza stała ścieżka, zaufany katalog, zakaz podmiany pliku i projekt jednej globalnej wyłączności. Przerwanie tworzenia pliku przed inicjalizacją może pozostawić pustą bazę, którą następne uruchomienie odrzuci; automatyczne odzyskiwanie i alarm nie są jeszcze wdrożone.

Model zapisuje stan `pending`, pozwala trwale zarezerwować jeden wpis jako `running` i po ponownym przejęciu blokady przenosi pozostawiony `running` do `uncertain`. Niepewny wpis blokuje kolejne rezerwacje; nie jest automatycznie ponawiany ani nazywany wykonanym. Nie ma jeszcze stanu `completed`, wywołania kontrolera, zapisu GitHuba, ponowienia po 120 sekundach, monitoringu ani archiwizacji. Nie włączono produkcyjnego webhooka i nie stosuje się tego magazynu do rzeczywistej pracy. Testy używają wyłącznie tymczasowych baz i syntetycznych danych; ponowne otwarcie oraz zakończenie procesu nie są testem restartu serwera ani awarii sprzętu.
